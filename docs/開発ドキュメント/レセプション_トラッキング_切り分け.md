# レセプションモード トラッキング 切り分け手順

トラッキングが動かない場合、以下の順で確認し、どこで止まっているかを特定してください。

---

## 前提

- **ディスプレイPC**: AI-Board のトップ (`https://<IP>:5000/`) を開き、**Reception** ボタンを押してレセプションモードにしておく。
- **受付PC**: `https://<IP>:5000/operator` を開き、**受付開始** を押す。

---

## 1. 受付PC（オペレーター）側の確認

ブラウザで **F12** → **コンソール** を開く。

### 1-1. Socket 接続確認

```javascript
_operatorSocket.connected
```

- **true** → サーバーに接続済み。次へ。
- **false** → 接続切れ。ページ再読み込みか、サーバー・ネットワークを確認。

### 1-2. テスト用トラッキングを手動送信

ディスプレイ側で Reception を選択した状態で、**受付PCのコンソール**で実行:

```javascript
_operatorSocket.emit('tracking_data', {
  timestamp: Date.now(),
  pose: { Spine: { x: 0.1, y: 0, z: 0 }, Head: { x: 0.05, y: 0, z: 0 } },
  face: { eye: { l: 1, r: 1 }, mouth: { x: 0 } }
});
```

- **ディスプレイのアバターが動く** → 受付PC→サーバー→ディスプレイの経路は正常。問題は「受付開始」後の MediaPipe/Kalidokit の送信側。
- **動かない** → 2. ディスプレイ側の確認へ。

### 1-3. 受付開始後の送信確認

「受付開始」を押したまま、**AI-Board サーバーを起動しているターミナル**を確認する。

- 約3秒に1回 **「[tracking_data] received from operator, relaying to others」** が出る → オペレーターから送信できている。2. ディスプレイ側を確認。
- **まったく出ない** → オペレーター側で `tracking_data` が送られていない（MediaPipe/Kalidokit のエラーや `onHolisticResults` が呼ばれていない可能性）。オペレーターのコンソールに Kalidokit / Holistic のエラーが出ていないか確認する。

---

## 2. ディスプレイPC側の確認

AI-Board のトップ (`https://<IP>:5000/`) を開き、**Reception** を選択した状態で **F12** → **コンソール**。

### 2-1. モードと VRM の確認

```javascript
console.log('currentMode:', window.currentMode);
console.log('applyTrackingData:', typeof window.applyTrackingData);
console.log('currentVrm:', window.currentVrm ? 'loaded' : 'null');
```

- **currentMode** が `'reception'` でない → 画面上で **Reception** をクリックする。
- **applyTrackingData** が `'function'` でない → ページ読み込み直後で VRM 未読み込みの可能性。少し待って再実行。
- **currentVrm** が `null` または `undefined` → **アバター（VRM）が読み込まれていません。** これが原因でトラッキングが効きません。
  - コンソールに **「VRM Loaded」** が出ているか確認。出ていなければ VRM 読み込みが完了していないか失敗している。
  - **「VRM load error」** や **「アバターの読み込みに失敗しました」** が出ていれば、`/static/avatar.vrm` の取得に失敗（404・ネットワークエラー等）。ディスプレイを開いた URL（https://&lt;IP&gt;:5000/）とサーバーが同一か、静的ファイルが配信されているか確認する。
  - ページを開いてから数秒待ってからもう一度 `window.currentVrm` を確認する（読み込み完了後に `window.currentVrm` が設定される）。

### 2-2. トラッキング受信の確認

コンソールに **「Reception: tracking_data received」** が約3秒ごとに出るか確認。

- **出る** → ディスプレイは `tracking_data` を受信している。`applyTrackingData` 内の pose/face の適用ロジックや VRM の骨名を疑う。
- **出ない** → サーバーから届いていない。3. サーバー側の確認へ。

---

## 3. サーバー（AI-Board）側の確認

AI-Board を起動しているターミナル（PowerShell 等）のログを確認。

### 3-1. トラッキング中継ログ

「受付開始」してカメラを向けた状態で、約3秒に1回、次のような行が出るか確認:

```
[tracking_data] received from operator, relaying to others (pose=True, face=True)
```

- **出る** → サーバーはオペレーターから受信し、他クライアントへ配信している。届いていないならディスプレイの Socket 接続や同一サーバーかどうかを確認。
- **出ない** → オペレーターから `tracking_data` が送られていない。1. 受付PC側（特に 1-3）を再確認。

---

## 3.5. サーバーで face のキーを確認する（表情が動かないとき）

AI-Board サーバーのターミナルに、**初回のみ** 次のような行が出ます:

```
[tracking_data] face keys: ['eye', 'mouth', ...], eye: ['l', 'r'] or ['left', 'right'], mouth: ['x'] or ['open']
```

- **eye** が `['l', 'r']` → ディスプレイ側はそのまま適用可能。
- **eye** が `['left', 'right']` → ディスプレイ側で `.left` / `.right` 対応済み。
- 上記と違うキー名の場合は、`applyTrackingData` の face 適用部分をそのキーに合わせて修正する必要あり。

---

## 3.6. 「tracking_data received」は出るが表情・体が動かない場合

- **currentVrm が null のとき**  
  `applyTrackingData` の先頭で return するため、**一切適用されません**。  
  - ディスプレイは **アバターが表示されているタブ** のコンソールで確認する（別タブだと別ページのため null になることがある）。  
  - ページを開いてから **数秒待って**「VRM Loaded」が出たあと、もう一度 `window.currentVrm` を確認する。  
- **「Reception: data sample」ログ**  
  カメラから届いているデータの形を確認できる。`face.eye` / `face.mouth` のキー名や値が想定と違うと表情が動かないことがある。

---

## 3.7. 「tracking_data received」は出るが hasPose: false の場合

- **hasFace: true, hasPose: false** → 顔データだけ届いている。ポーズ（体）はオペレーター側で検出されていないか、Kalidokit Pose が null を返している。
  - **オペレーター**: カメラに**上半身全体**が映っているか、明るさは十分か確認する。MediaPipe は体が隠れていると poseLandmarks を出さないことがある。
  - **ポーズ送信の改善**: オペレーター側で Kalidokit Pose.solve に `imageSize: { width, height }` を渡すようにした（未指定だと null になりやすいため）。
- **顔は届いているがアバターの目・口が動かない** → VRM の表情名が違う可能性。使用中の VRM が `blink` / `blinkLeft` / `blinkRight` / `aa` を持っているか確認する。

---

## 4. チェックリストまとめ

| 確認項目 | 場所 | 期待 |
|----------|------|------|
| Socket 接続 | 受付PC コンソール `_operatorSocket.connected` | true |
| 手動 emit でアバターが動くか | 受付PCで `_operatorSocket.emit('tracking_data', {...})` | ディスプレイのアバターが動く |
| currentMode | ディスプレイ コンソール `window.currentMode` | 'reception' |
| applyTrackingData / currentVrm | ディスプレイ コンソール | 両方あり |
| 「Reception: tracking_data received」 | ディスプレイ コンソール | 約3秒ごとに出る |
| 「[tracking_data] received from operator」 | サーバー ターミナル | 約3秒ごとに出る |

---

## 5. 手動送信で動くが、受付開始だと動かない場合

- オペレーター側で **MediaPipe Holistic** や **Kalidokit** がエラーで止まっている、または `onHolisticResults` が呼ばれていない可能性が高い。
- オペレーターのコンソールに **Kalidokit** / **Holistic** / **Module.arguments** などのエラーが出ていないか確認する。
- 「受付終了」→「受付開始」の再開で Holistic が落ちる問題は、Holistic を閉じずに再利用する修正済み。**ページを開き直してから**「受付開始」のみ行うと安定しやすい。
