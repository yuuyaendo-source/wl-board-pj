# 全体を通しての改善点と一般リリース時の問題点

プロジェクト全体の改善が必要な点と、このプロダクトを一般リリースする場合に解消すべき問題点をまとめています。

---

## 1. セキュリティ

### 1.1 認証・アクセス制御の欠如

| 対象 | 現状 | 一般リリース時の問題 |
|------|------|----------------------|
| **/manager**（名前・顔管理） | 誰でもアクセス可能 | 第三者による登録者一覧の閲覧・顔データの取得・登録の改ざん・削除が可能 |
| **/operator**（受付オペレーター） | 誰でもアクセス可能 | 任意の人がトラッキングを送信し、ディスプレイのアバターを操作できる |
| **顔登録 API**（POST/PUT/DELETE `/api/face_registry`） | 認証なし | 管理者以外が名前・顔の登録・更新・削除を行える |
| **Webhook**（`/api/receive_note`） | 認証なし | 任意のクライアントが付箋データを送信し、AIコメント・音声を濫用できる |
| **画像アップロード**（`/api/upload`, `/api/upload_image`） | 認証なし | 不正な画像アップロード・ストレージ枯渇・悪用のリスク |

**推奨**: 管理者・オペレーター用ページおよび API に認証（ログイン／トークン／IP制限など）を導入する。Webhook には共有シークレットや署名検証を検討する。

### 1.2 秘密情報の扱い

| 項目 | 現状 | 問題 |
|------|------|------|
| **Flask SECRET_KEY** | `app.config['SECRET_KEY'] = 'secret!'` とハードコード | セッション改ざん等のリスク。本番では環境変数から読み込むべき |
| **.env.example** | `GEMINI_API_KEY=AIzaSy...` のように実キー風の値が記載されている可能性 | サンプルとしてプレースホルダー（例: `your_gemini_api_key_here`）にすべき。実キーは絶対に含めない |
| **RTSP_URL** | `.env.example` に `rtsp://admin:password@...` の例 | 本番用の認証情報は例示に含めず、プレースホルダーのみにする |

### 1.3 CORS・公開範囲

| 項目 | 現状 | 問題 |
|------|------|------|
| **Socket.IO** | `cors_allowed_origins="*"` | 任意オリジンから接続可能。本番では許可オリジンを限定すべき |
| **Postit (02_1)** | `Access-Control-Allow-Origin: '*'` | 同上。必要に応じてオリジンを制限する |

### 1.4 TLS・証明書

| 項目 | 現状 | 問題 |
|------|------|------|
| **HTTPS** | 自己署名証明書（`generate_cert.py`） | 一般ユーザーはブラウザの警告に遭遇する。公的なサービスでは CA 署名証明書または Let's Encrypt 等の利用を検討 |
| **cert.pem / key.pem** | リポジトリにコミットされている可能性 | 秘密鍵は .gitignore に含め、リポジトリに含めない |
| **Postit → AI-Board** | 開発時 `NODE_TLS_REJECT_UNAUTHORIZED='0'` で自己証明書を許可 | 本番では無効化し、正しい証明書で接続する |

## 2. プライバシー・法務

### 2.1 顔データ・個人情報

| 項目 | 現状 | 一般リリース時の問題 |
|------|------|----------------------|
| **顔の登録・照合** | 顔画像（base64）をサーバー上の JSON で保存 | 個人の同意・利用目的の明示・保存期間の規定がなく、個人情報保護法・GDPR 等の観点でリスク |
| **カメラ映像** | `/camera_stream` で MJPEG 配信、ブラウザで顔検知 | 利用規約・プライバシーポリシーで「カメラ利用・顔検知」を明示し、同意取得が必要 |
| **名前・顔の紐付け** | 実名と顔データを紐付けて保存 | 要配慮個人情報に該当する可能性。取得・利用・第三者提供のルールを文書化する必要 |

**推奨**: 利用規約・プライバシーポリシーの整備、同意フローの実装、顔データの最小化・保存期間の設定、必要に応じて匿名化や削除手段の提供。

### 2.2 利用規約・ライセンス

- **利用規約**: 一般リリース時には、利用目的・禁止事項・免責・責任範囲を明文化する必要がある。
- **第三者コンポーネント**: VOICEVOX・Gemini API・MediaPipe・Kalidokit 等の利用条件（API 利用規約・ライセンス）に準拠し、再配布・商用利用の可否を確認する必要がある。

## 3. 運用・デプロイ

### 3.1 本番環境の想定不足

| 項目 | 現状 | 問題 |
|------|------|------|
| **起動方法** | `start_all_servers.ps1` で手動起動・Windows PowerShell 前提 | Linux サーバー・コンテナ・オートスケールを想定した手順・スクリプトがない |
| **プロセス管理** | 単一プロセスで起動、落ちたら手動再起動 | systemd・PM2・Docker 等による自動再起動・ヘルスチェックがない |
| **ログ** | 主に `print` でコンソール出力 | ローテーション・レベル・外部送信がなく、障害調査がしづらい |
| **設定** | `config.json`・`.env` が開発向け | 本番用の設定例・環境別（dev/staging/prod）の切り替えが未整備 |

### 3.2 スケーラビリティ・可用性

- **状態**: 付箋状態・`last_comment_time`・`mobile_notes_data` 等をメモリ上で保持。複数インスタンスや再起動で状態が失われる。
- **顔登録**: 現状はローカル JSON。複数サーバーやバックアップ・リストアの手順が未整備。
- **セッション**: Flask のセッションがメモリ前提。スティッキーセッションや外部セッションストアの検討が必要になる可能性。

### 3.3 依存サービスの扱い

- **VOICEVOX**: ローカル起動前提。落ちていると音声生成が失敗する。エラーハンドリング・フォールバック・ヘルスチェックの明文化があるとよい。
- **Gemini API**: キー・クォータ・レート制限・障害時の挙動をドキュメント化し、必要ならリトライ・キュー・フォールバックを検討。
- **02_1 (Postit)**: AI-Board が `BOARD_APP_URL` に依存。Postit が落ちている場合の挙動・リトライ・ユーザーへの通知が未整備。

## 4. 品質・保守性

### 4.1 テスト

| 項目 | 現状 | 問題 |
|------|------|------|
| **単体テスト** | 実質なし（`test_gemini.py` 等の確認用スクリプトはあるがテストフレームワークではない） | リグレッションの検知が難しく、一般リリース後の変更が危険 |
| **API テスト** | なし | エンドポイントの契約・エラーレスポンスが保証されない |
| **E2E テスト** | なし | ブラウザ・カメラ・Socket.IO を伴うフローの品質保証が手作業依存 |

**推奨**: 重要 API とコアロジックの単体テスト、主要画面の E2E テストを段階的に導入する。

### 4.2 エラーハンドリング・入力検証

| 項目 | 現状 | 問題 |
|------|------|------|
| **API 入力** | 付箋テキスト・名前・顔データ等のバリデーションが最小限 | 不正な長さ・形式・文字コードでエラーや不安定動作の可能性 |
| **ファイルアップロード** | ファイルサイズ・形式の制限が不明瞭 | 巨大ファイルや悪意ある形式による DoS・ストレージ枯渇のリスク |
| **エラーレスポンス** | 一部で `str(e)` をそのまま返す | 内部情報が漏れ、デバッグしやすい反面、本番では不適切な場合がある |

**推奨**: 入力の長さ・形式・必須項目のチェック、アップロードのサイズ上限・Content-Type 制限、本番では汎用エラーメッセージに統一する。

### 4.3 レート制限

- **現状**: 付箋ごとの AI コメントは 10 秒間隔でレート制限あり。その他の API（顔登録・アップロード・Webhook）はレート制限なし。
- **問題**: 悪意ある大量リクエストで API・Gemini・VOICEVOX が枯渇したり、サービスが利用不能になるリスク。
- **推奨**: 認証と合わせて、IP またはユーザー単位のレート制限を検討する。

## 5. 機能・UX の未完成部分

### 5.1 既知の制限（ドキュメント済み）

- **Reception モード**: トラッキングのずれ・不安定さが残り、「調整が必要」と明記されている。一般リリース前に安定化・チューニングが望ましい。
- **名前・顔照合**: 簡易的な画像類似度（グレースケール MSE）で閾値も要調整。誤認証・なりすましのリスクを説明し、必要なら精度の高い方式（顔埋め込み等）を検討。
- **自動パーソナル切替**: SASE 等で Face Detector API が使えない場合は MediaPipe にフォールバック。CDN がブロックされると「MediaPipe で検知できませんでした」となる。環境要件を利用者に明示する必要がある。

### 5.2 未実装・今後の予定

- **Phase 2B: 音声統合**（WebRTC 双方向音声・リップシンク）が未実装。受付モードで「声」を通すにはこれが前提。
- **Phase 2C: UI 改善**（接続状態インジケーター、音声レベル・ミュート/音量）が未実装。運用時の見やすさ・操作性に影響する。
- **管理者認証**: 設計メモで「別フェーズで検討」とされている。一般リリースでは必須に近い。

## 6. ドキュメント・サポート

### 6.1 利用者向け

- **インストール・セットアップ**: 開発者向け README は充実しているが、非技術者や「一般リリース版」を想定した手順（インストーラ・設定ウィザード等）はない。
- **トラブルシューティング**: `レセプション_トラッキング_切り分け.md` 等はあるが、よくある質問（FAQ）やサポート窓口の記載はない。
- **バージョン・更新**: バージョニング方針・互換性・更新手順が文書化されていない。

### 6.2 開発者向け

- **API 仕様**: エンドポイント一覧・リクエスト/レスポンス形式が 1 か所にまとまった API ドキュメントがない。
- **アーキテクチャ**: 全体構成・データフロー・モード切替の流れを説明する図・ドキュメントがあると、新規参加者や保守に有利。

---

## 7. まとめ：一般リリース前に優先して対応したい項目

| 優先度 | カテゴリ | 項目 |
|--------|----------|------|
| **高** | セキュリティ | /manager・/operator・顔登録 API の認証、SECRET_KEY の環境変数化、.env.example のプレースホルダー化 |
| **高** | プライバシー・法務 | 利用規約・プライバシーポリシー、顔・カメラ利用の同意フロー、保存期間・削除のルール |
| **高** | 運用 | 本番向け起動・プロセス管理・ログ方針、証明書（CA 署名または Let's Encrypt）の検討 |
| **中** | 品質 | 重要 API の単体テスト、入力検証・アップロード制限、レート制限の検討 |
| **中** | 機能 | Reception トラッキングの安定化、管理者認証の実装 |
| **中** | CORS・TLS | 本番での CORS オリジン限定、`NODE_TLS_REJECT_UNAUTHORIZED` の本番無効化 |
| **低** | ドキュメント | 利用者向けセットアップ・FAQ、API 仕様・アーキテクチャの文書化 |
| **低** | 今後の拡張 | Phase 2B（音声統合）、Phase 2C（UI 改善）、E2E テストの導入 |

上記は「研究室・社内利用」から「不特定多数への一般リリース」に踏み切る際に、特に洗い出し・対応が必要な項目です。段階的に優先度の高いものから対応することを推奨します。
