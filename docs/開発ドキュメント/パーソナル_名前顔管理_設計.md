# パーソナルモード 名前・顔管理 設計メモ

パーソナルモードの「任意切り替え時は名前と顔が一致した場合に有効」を実現するための設計です。将来的に S3 等のクラウドストレージを使うことを想定し、**顔と名前の管理は特定の人物（管理者）が行う**前提で整理しています。

---

## 1. 役割の整理

| 役割 | 誰 | やること |
|------|-----|----------|
| **管理者** | 特定の人物（1名または少数） | 名前の追加・削除、各名前に対する「顔」の登録・更新。管理用画面（/manager）のみ利用。 |
| **利用者** | エントランスを利用する人 | パーソナルモードに切り替えるとき、自分の名前を選び、カメラで顔を照合して本人確認。 |

- 管理者以外は名前・顔の登録・変更は行わない。
- 表示側（index）では「名前の一覧取得」と「顔の照合」のみ行い、登録・変更は行わない。

---

## 2. データの形（名前・顔）

- **1人あたり**: 識別子（id）、表示名（name）、顔データ（faceData）。
- **顔データ**: 現状は「登録時に撮影した1枚の顔画像（base64 JPEG 等）」を想定。将来は S3 上のオブジェクト URL や、顔埋め込みベクトルなどに拡張可能。
- **一覧**: 照合時に「名前の一覧」だけ返す API と、「特定1人の名前＋顔データ」を返す API を分けると、S3 に移行したときも同じインターフェースを維持しやすい。

例（現状のイメージ）:

```json
{
  "persons": [
    { "id": "uuid-1", "name": "田中", "faceData": "data:image/jpeg;base64,..." },
    { "id": "uuid-2", "name": "佐藤", "faceData": "..." }
  ]
}
```

将来 S3 を使う場合:

- 顔データを S3 に保存し、`faceData` を S3 の URL やキーにする。
- 一覧 API は「id + name」のみ返し、照合用に「1人分の顔データ取得」を別 API にすると、S3 の署名付き URL を返す実装に差し替えやすい。

---

## 3. ストレージの抽象化（将来 S3 対応）

- **現状**: サーバー上の JSON ファイル（例: `data/face_registry.json`）に保存。管理者用 API と表示側の照合用 API は、この「ストレージ層」の上に載せる。
- **将来**: 同じ API 仕様を保ったまま、ストレージ実装だけ差し替え。
  - 例: `FaceRegistryStorage` のようなインターフェースを用意し、
    - 現行: ローカルファイル読み書き
    - 将来: S3 のバケット／プレフィックスを利用（一覧は S3 list、1件取得は S3 get、登録・更新は S3 put、削除は S3 delete）
- データの形（id, name, faceData の意味）は変えず、**保存先だけが「ローカル → S3」に変わる**ようにする。

これにより、「顔と名前の管理は特定の人物が行う」という運用はそのままで、保存先だけクラウドに移行できます。

---

## 4. 管理者用機能（誰が何をするか）

- **管理者**が行う操作は次のとおり（すべて管理用画面から実行する想定）。
  1. **名前の追加**: 表示名を入力して登録。id はサーバーで発行。
  2. **顔の登録・更新**: 対象者を選び、カメラで1枚撮影して「この人」の顔として保存。
  3. **名前の削除**: 不要になった人を一覧から削除（顔データも一緒に削除）。

- 上記はすべて **管理用 API** 経由で行い、その API は「管理者が使う画面」からのみ呼ぶ想定でよい。
- 認証・アクセス制御（管理者だけが /manager や管理用 API にアクセスできるようにする）は、別フェーズで検討。

---

## 5. 表示側（パーソナルモード任意切替）の流れ

1. 利用者が「Personal」を選択。
2. 名前・顔照合が有効な場合:
   - サーバーから「名前の一覧」を取得し、利用者に名前を選ばせる。
   - 選んだ名前（id）に対応する「顔データ」をサーバーから取得（現状は JSON 内、将来は S3 等から取得）。
   - カメラで現在の顔を取得し、登録顔と照合（ブラウザ内またはサーバーで比較）。
   - 一致した場合のみパーソナルモードに切り替え。一致しなければ「名前と顔が一致しません」等を表示して切り替えしない。
3. 名前・顔の登録が0件のときは、現状どおり照合なしでパーソナルモードに切り替えてもよい（運用で決める）。

---

## 6. 今後の拡張（S3 を想定したとき）

- ストレージ層を「ローカルファイル」から「S3」に差し替える。
- 顔データの保存先を S3 オブジェクトにし、必要に応じて署名付き URL で取得する。
- 管理者の「顔の登録」は、アップロード先を S3 にする（同じ API の裏側だけ S3 put に変更）。
- 「名前の一覧」「1人分の取得」「登録・更新・削除」の API 仕様は変えず、ストレージ実装だけ差し替える形にすると、既存の管理画面・表示側の処理をほぼそのまま使える。

---

## 7. まとめ

- **顔と名前の管理は特定の人物（管理者）が行う** → 管理用画面（/manager）と管理用 API で完結。
- **将来的に S3 等を使う** → ストレージ層を抽象化し、現状はローカル、将来は S3 に差し替え可能にしておく。
- データの形（id, name, faceData）と API の役割をいまの段階で決めておくことで、後からクラウドストレージに移行しやすくする。
