# Project: Wonder Rinko (ワンダーリン子) - CES 2028 RoadMap

## 1. Project Vision & Philosophy
**"Retrofit the Intelligence"（知性の後付け）**
本プロジェクトは、建設・施工会社発の「空間OS」開発プロジェクトである。
既存の古いオフィス設備（Legacy）に対し、AI（Brain）とネットワーク（Nerves）を後付け（Retrofit）することで、物理的な操作を伴うスマートビル化を実現する。

* **Goal:** CES 2028への出展と、グローバルな「施工 × IT」パッケージの販売。
* **Core Value:** 「アプリ上の便利」ではなく、「物理的な空間制御（鍵、空調、配線）」を提供する。
* **Role of Rinko:** 単なるチャットボットではなく、設備を管理し、社員の創造性を引き出す「空間の管理人（Admin）」。

## 2. System Architecture
システムは以下の3層で構成される。AIエージェントは各層の連携を意識してコードを生成すること。

### Layer 1: Brain (Logic & AI)
* **Core:** Python (FastAPI / Local Scripts)
* **AI Model:** Google Gemini Pro (via API)
* **Features:**
    * **RAG:** 社内マニュアル、図面、過去のトラブルシューティングの参照。
    * **Function Calling:** AIの判断による物理デバイス制御（照明ON/OFFなど）。
    * **Human-in-the-loop:** AIが解決できない場合、遠隔の人間オペレーターに通話・操作をスイッチする。

### Layer 2: Nerves (Network & Security)
* **Connectivity:** **Cloudflare Tunnel (`cloudflared`)**
    * *重要:* 設置先のネットワーク環境（ファイアウォール/NAT）に依存せず、外部から安全に接続できる構成とする。
* **Infrastructure Management:**
    * **Cisco Meraki API:** ネットワークトラフィック、混雑状況の取得。
    * **CATO Networks:** セキュアなWAN接続（監視対象）。
* **Agility:** ネットワークが切断されてもローカル機能（自己診断等）は維持する。

### Layer 3: Body (Physical Interface)
* **Kiosk (什器):**
    * Verkada Cameras (顔認証・動体検知)。
    * Display (Next.js / React によるダッシュボード)。
    * Local Sensors (Modbus / GPIO / USB-RS485)。
* **Device Control:**
    * Raspberry Pi + Relay Module (電気錠、照明の物理スイッチ制御)。
    * Infrared Blaster (業務用エアコン制御)。
* **PC Agent:** 社員PCに常駐するPythonアプリ。

## 3. Key Components & Implementation Guide

### A. Wonder Rinko Kiosk (The Space Admin)
什器型のメインシステム。以下の3モードを自動で切り替える（State Machine）。

1.  **AI Board Mode (Ambient):**
    * 待機状態。CATO/Merakiのトラフィック、CO2濃度などをSFチックに可視化。
    * 「付箋（物理）」をカメラで認識し、トラブル箇所としてデジタルツインにプロットする。
2.  **Reception Mode (Physical):**
    * Verkadaで人を検知 → 挨拶。
    * 顔認証 → 社員なら「Aさん、お疲れ様です」＋個別の通知。
    * ゲストなら → アナログな手書きパスの発行や、物理ゲートの解錠。
3.  **Personal Mode (Remote):**
    * 複雑な相談対応。必要に応じてHuman-in-the-loopで「中の人」が対応。

### B. Personal Rinko Agent (The Nudge)
社員PC（Windows/Mac）に常駐する軽量Pythonアプリ。
**「多機能」を目指さず、「行動のトリガー」に特化する。**

* **UI/UX Rule:** ポータル画面（Menu）を経由させない。「通知」をクリックしたら、目的のURL（SaaSの入力画面や会議URL）が**直接ブラウザで開く（Deep Link）**仕様とする。
* **Tech Stack:** `pystray`, `win10toast` (Windows), `plyer` (Mac).
* **Triggers:**
    * **Time:** 「月末です。経費精算画面を開きますか？」
    * **Status:** CPU負荷低（暇）→「現場のアイデア投稿しませんか？」
    * **Location:** 会議室Wi-Fi接続 →「議事録フォーマットを開きますか？」

## 4. Development Constraints & Anti-Patterns (Do's and Don'ts)

* **Do Not Build General AI:**
    * 雑談能力（IQ）はGoogle Geminiに任せる。我々が開発するのは「社内コンテキスト（RAG）」と「物理制御（Function Calling）」のみ。
* **Do Not Aim for Consumer IoT:**
    * 家庭用スマートホーム（Alexa等でできること）は範囲外。
    * **ターゲットは「業務用機器（Professional Gear）」**。電気工事士資格が必要な領域（盤内配線、業務用空調）の制御を優先する。
* **Focus on Retrofit:**
    * 常に「既存の古い設備とどう融合するか」を考える。
    * 物理スイッチへのリレー割り込みや、赤外線ハックを推奨。
* **Network Agnostic:**
    * 「Merakiがないと動かない」はNG。MerakiがあればAPIを使う、なければローカル診断をするような分岐処理を入れること。

## 5. Required Tech Stack for Code Generation

AIエージェントは以下のライブラリ・技術を優先して使用すること。

* **Language:** Python 3.10+
* **Web/API:** `FastAPI`, `requests`
* **GUI (PC Agent):** `pystray`, `PySide6` (if needed for complex UI)
* **Network/IoT:** `paho-mqtt`, `pymodbus`, `meraki` (SDK)
* **AI:** `google-generativeai` (Gemini API), `langchain` (for RAG structure)
* **Infra:** Docker, Cloudflare Tunnel (`cloudflared`)
