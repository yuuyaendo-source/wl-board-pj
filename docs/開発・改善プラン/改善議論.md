音声・双方向コミュニケーション設計
1. 音声出力の選択肢
Option A: VOICEVOX音声で対応
仕組み:

受付担当者がテキスト入力 → VOICEVOX生成 → エントランスで再生
または、音声認識（Web Speech API）→ テキスト化 → VOICEVOX → 再生
メリット:

✅ 既存のVOICEVOX統合を活用
✅ リップシンクが正確（音声波形解析済み）
✅ 通信量が少ない（テキストのみ送信）
✅ 音質が安定（合成音声）
✅ キャラクター性を維持（リン子の声）
デメリット:

❌ 生成に遅延がある（0.5〜1秒程度）
❌ 自然な会話感が損なわれる
❌ 感情表現が限定的
❌ 受付担当者の「人間らしさ」が伝わらない
推奨用途:

定型的な案内（「お待ちください」「〇〇へご案内します」など）
AI-Boardモードからの自動応答
Option B: 遠隔から音声も送信（リアルタイム音声）
仕組み:

受付担当者のマイク → WebRTC/Socket.IO → エントランスのスピーカー
リップシンクは音声波形解析（AudioContext）で実現
メリット:

✅ 自然な会話が可能
✅ 遅延が少ない（WebRTC: 100ms以下）
✅ 感情・ニュアンスが伝わる
✅ 「人が対応している」感が強い
デメリット:

❌ 通信量が多い（音声ストリーム）
❌ ネットワーク品質に依存
❌ リップシンクの精度が若干落ちる可能性
❌ キャラクター性が薄れる（リン子の声ではない）
推奨用途:

複雑な問い合わせ対応
緊急時の対応
VIP来客対応
推奨案: ハイブリッド方式
[通常時]
AI-Board Mode → VOICEVOX（自動応答）
[受付対応時]
Remote Reception Mode → リアルタイム音声送信（受付担当者の声）
  ↓
  オプション: 「VOICEVOX変換モード」ON/OFF切替可能
  - ON: 受付担当者の音声 → 音声認識 → テキスト → VOICEVOX → 再生（キャラ声維持）
  - OFF: 受付担当者の音声 → 直接再生（自然な会話）
理由:

柔軟性: 状況に応じて使い分け可能
段階的実装: まずリアルタイム音声、後でVOICEVOX変換追加
UX: 来客者は「人が対応している」と感じつつ、キャラクター性も維持可能
2. 双方向コミュニケーション（来客者の声を受付担当者へ）
必要な機能
[来客者] → [エントランスPC マイク] → [受付担当者PC スピーカー]
実装方法
Option A: WebRTC（推奨）
仕組み:

エントランスPCと受付担当者PCでWebRTC P2P接続
双方向音声ストリーム
メリット:

✅ 低遅延（100ms以下）
✅ 双方向が標準機能
✅ ブラウザ標準API
デメリット:

❌ 実装がやや複雑（シグナリングサーバー必要）
❌ ファイアウォール/NAT問題の可能性
実装例:

// SimplePeer.js などのライブラリ使用
const peer = new SimplePeer({ initiator: true, stream: localStream });
peer.on('signal', data => socket.emit('webrtc-signal', data));
peer.on('stream', remoteStream => audioElement.srcObject = remoteStream);
Option B: Socket.IO音声ストリーミング
仕組み:

マイク → AudioContext → PCMデータ → Socket.IO → 再生
メリット:

✅ 既存のSocket.IO活用
✅ 実装がシンプル
デメリット:

❌ 遅延が大きい（300ms〜1秒）
❌ 通信量が多い
❌ 音質が劣化しやすい
推奨: WebRTC（SimplePeer.js使用）
理由:

リアルタイム性が重要（受付対応）
双方向が標準
ライブラリで実装簡略化

Display PC (来客) ◄──WebRTC P2P──► Operator PC (受付)
