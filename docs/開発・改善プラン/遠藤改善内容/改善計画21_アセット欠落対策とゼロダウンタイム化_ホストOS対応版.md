# 改善計画21：デプロイ時のアセット欠落によるクラッシュ（Offline化）の抜本的対策とゼロダウンタイム化（ホストOS対応版）

## 1. 概要・目的
Blue/Greenデプロイメントの実行時、旧バージョンの画面を開いたままのユーザーのブラウザが旧JSファイル（静的アセット）を要求した際、取得に失敗してアプリがクラッシュ（`Unexpected token '<'` および `🔴 Offline`）する問題を完全に解決します。

Next.jsの仕様と現在のインフラ環境（NginxがホストOS上で直接稼働）に合わせた「静的ファイルのホストOSディレクトリでの永続化＋Nginx直接配信および確実な404返却」を導入し、デプロイ時のエラーを撲滅してユーザーにダウンタイムを感じさせないシームレス・アップデートを実現します。

## 2. 原因の整理と改善アプローチ

* **原因のメカニズム**:
  1. `deploy.sh` により新コンテナ（board-system）または新プロセス（wl-sticky-note）が起動し、トラフィックが切り替わった後、旧コンテナ/プロセスが停止・破棄されます。
  2. 開いたままのブラウザは旧バージョンのHTMLを持っているため、破棄された環境内にしか存在しないJSファイルを要求し続けます。
  3. この要求に対し、本来 404 が返るべきところ、Next.jsのフォールバック機能やルーティングの都合によりHTMLが返却される（または302リダイレクトされる）事象が発生します。
  4. ブラウザが受け取ったHTMLをJSとしてパースしようとして `SyntaxError` となり、処理が停止して `🔴 Offline` のまま固まります。

* **改善アプローチ（ベストプラクティス）**:
  1. **アセットのホストOSディレクトリ化とNginx配信**: デプロイ時にビルドされたアセットディレクトリをホストOS上の特定ディレクトリに蓄積・同期します。このディレクトリをホストOS上のNginxから直接配信させることで、旧アセットの確実な配信を維持します。
  2. **確実な404の返却と自動リカバリ**: Nginxのルーティング（`/_next/static/`）で `try_files $uri =404;` を設定し、存在しない古いアセットが要求された場合、Next.jsアプリに流さずにNginxが直接純粋な404ステータスを返します。これにより、Next.jsの組み込みリカバリ機構（`ChunkLoadError` 検知による自動ハードリロード）が正しくトリガーされます。
  3. **自動クリーンアップ**: ホストOSのストレージ肥大化を防ぐため、デプロイ時に一定期間経過した古いアセットを自動削除します。

## 3. 具体的な実装仕様とスクリプトコード

### インフラ側の静的アセット永続化・Nginx直接配信

#### 1. `deploy.sh` への同期・クリーンアップ処理追加

**① Board System (Dockerコンテナ) の場合:**
ホストOS上のディレクトリ作成、コンテナからのファイル同期、権限設定、古いファイルの削除処理をデプロイスクリプトに追加します。

```bash
# board-system/deploy/deploy.sh (デプロイ起動・ヘルスチェック後の適切な箇所に追記)

# ホストOS上に静的アセット用のディレクトリを作成
STATIC_DIR="/var/www/wlinko-pj/shared_static/frontend"
mkdir -p "$STATIC_DIR"

FRONTEND_CONTAINER=$(docker compose -f "$DOCKER_COMPOSE_FILE" -p "board-system-$NEW_COLOR" ps -q frontend)

if [ -n "$FRONTEND_CONTAINER" ]; then
    echo "Syncing static assets to host directory..."
    # コンテナからホストOSのディレクトリへ直接上書きコピー
    docker cp ${FRONTEND_CONTAINER}:/app/.next/static/. "$STATIC_DIR/"
    # Nginxが安全に読み取れるようにパーミッションを調整 (ディレクトリは実行権限、ファイルは読み取り権限)
    chmod -R a+rX "$STATIC_DIR"
else
    echo "Warning: Frontend container not found, skipping static assets sync."
fi

# クリーンアップ (14日以上古いファイルを削除し、空ディレクトリも整理)
echo "Cleaning up old static assets..."
find "$STATIC_DIR" -type f -mtime +14 -delete
find "$STATIC_DIR" -type d -empty -delete
```

**② wl-sticky-note (PM2/ホストOS稼働) の場合:**
`wl-sticky-note` はPM2を使用してホストOS上で直接稼働しているため、ビルドされた `.next/static` ディレクトリをそのままコピーして蓄積します。

```bash
# wl-sticky-note/src/deploy.sh (npm run build の後の適切な箇所に追記)

STATIC_DIR_STICKY="/var/www/wlinko-pj/shared_static/sticky-note"
mkdir -p "$STATIC_DIR_STICKY"

echo "Syncing sticky-note static assets..."
# ビルドで生成された .next/static を蓄積ディレクトリにコピー
cp -a .next/static/. "$STATIC_DIR_STICKY/"
chmod -R a+rX "$STATIC_DIR_STICKY"

echo "Cleaning up old sticky-note static assets..."
find "$STATIC_DIR_STICKY" -type f -mtime +14 -delete
find "$STATIC_DIR_STICKY" -type d -empty -delete
```

#### 2. `nginx.conf` での直接配信ルーティング
Next.js アプリへのプロキシ設定の手前に、`/_next/static/` に対する直接配信のルールを追加します。

```nginx
# nginx.conf

server {
    # 既存の設定...

    # Board System (Next.js) の静的アセットをホストOSから直接配信
    location /_next/static/ {
        alias /var/www/wlinko-pj/shared_static/frontend/;
        expires 365d;
        access_log off;
        # ファイルが見つからない場合は純粋な 404 を返し、Next.js に流さない
        # これにより、Next.jsクライアント側で ChunkLoadError が発生し自動リロードされる
        try_files $uri =404;
    }

    # wl-sticky-note が別パスでマウントされている場合
    location /board/_next/static/ {
        alias /var/www/wlinko-pj/shared_static/sticky-note/;
        expires 365d;
        access_log off;
        try_files $uri =404;
    }

    # その他の動的リクエストはプロキシへ流す
    location / {
        proxy_pass http://current_frontend; # Board System用
        # ... 既存の proxy_set_header 等
    }
}
```

## 4. 影響範囲・変更ファイル一覧

| ファイルパス | 変更区分 | 変更内容の概要 |
| :--- | :--- | :--- |
| `board-system/deploy/deploy.sh` | **MODIFY** | ホストOSディレクトリ作成、フロントエンドコンテナからの `docker cp` による同期、パーミッション設定（`chmod -R a+rX`）、および古いファイルの削除処理を追加。 |
| `wl-sticky-note/src/deploy.sh` | **MODIFY** | ホストOSディレクトリ作成、ビルド済み `.next/static` の `cp` による同期、パーミッション設定、およびクリーンアップを追加。 |
| `board-system/nginx/nginx.conf`等 | **MODIFY** | `location /_next/static/` ブロックを追加し、Nginxがホストディレクトリから直接ファイルを配信、不在時は `404` を返すようルーティングを変更。 |

※インフラ環境の実態に合わせているため、アプリケーションのコード修正およびDocker Compose設定ファイルの修正は不要です。

## 5. 検証および運用計画

1. **インフラ修正の反映確認**:
   - デプロイスクリプトを実行し、ホストOS上の `/var/www/wlinko-pj/shared_static/frontend/` および `sticky-note/` にファイルが同期されていること、またNginxからの読み取り権限が正しく付与されていることを確認。
   - `nginx.conf` の設定後、アプリ上の静的アセットのレスポンスヘッダを見て Nginx が直接配信しているか確認。
2. **ゼロダウンタイムおよびリカバリ検証**:
   - ブラウザでアプリを開いた状態でバックグラウンドでデプロイを実行し、旧コンテナ(プロセス)を停止させる。
   - アプリ上で画面遷移等の操作を行い、古いJSファイルが要求された際、ブラウザのNetworkタブで該当JSファイルが `404` となることを確認。
   - `SyntaxError` によるクラッシュが発生せず、Next.jsがエラーを検知して自動的にページがハードリロードされ、新バージョンが表示されることを確認。
3. **クリーンアップの検証**:
   - 運用中に 14日を超えたファイルおよび空ディレクトリが次回のデプロイ時に自動削除されるか、テスト環境（14日を数分に変更等）で確認する。
