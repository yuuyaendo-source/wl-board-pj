# 改善計画23：システム間連携の堅牢化・共通化およびテスト品質向上

## 1. 概要・目的

本計画では、現在稼働しているエコシステム全体（付箋ボード、Board System、デスクトップアプリ等）のさらなるスケールアウトと保守性の向上を目指し、以下の4つの課題に対する抜本的な改善を実施します。

単なる機能追加ではなく、**システム全体の信頼性（Reliability）・スケーラビリティ・保守性を向上させるフェーズ**として位置づけ、後々の手戻りや運用障害を防ぐための「設計上の留意点」をクリアにしながら進行します。

---

## 2. 改善提案の詳細と設計上の留意点

### ① データ永続化の堅牢化（wl-sticky-note の DB化・統合）

* **現状と課題**:
  `wl-sticky-note` において、付箋データが単一の `boards.json` ファイルへのデバウンス書き込み（一時ファイル作成→リネーム）で永続化されています。複数クライアントからの高頻度な同時操作やスケールアウト時に、ファイルアクセス競合や整合性喪失のリスクがあります。
* **改善案**:
  `board-system` と同じ PostgreSQL（または Redis 等の K/V ストア）を共有ストレージとして利用し、データの堅牢性とバックアップの一元化を図ります。Socket.IO のアダプター（Redis/Postgres）と連携させることで、無停止での水平スケールが可能になります。
* 🚨 **【設計上の留意点】**
  * **マイグレーション権限の一元化**: `board-system` 側は Alembic (Python) でスキーマを管理しています。Node.js 側 (Prisma 等) は `prisma db pull` (Introspection) を用いてスキーマと型のみを同期し、マイグレーションの主導権は Alembic に一本化して競合を防ぎます。
  * **キャンバス固有データ**: `sticky_notes` テーブルへの相乗りのほか、手書き線データ等用に `board_canvas_lines`（`board_id`, `x1`, `y1`, `x2`, `y2`, `color` 等）といった専用拡張テーブルの設計が必須です。
  * **高頻度座標更新の最適化**: ドラッグ中（100ms スロットル等）の座標を都度 DB へ `UPDATE` すると負荷が跳ね上がります。ドラッグ中の状態同期はインメモリ（Redis 等）や Socket.IO ブロードキャストで捌き、ドラッグ終了時（`mouseup` / `touchend`）に最終座標のみ DB へ書き込む二段階設計とします。

### ② ボード間・システム間の同期とエラーハンドリングの統一

* **現状と課題**:
  `board-system` から `wl-sticky-note` 等への通知（PATCH / POST）を非同期通信で行っており、失敗時はログ出力のみにとどまっています。ネットワーク瞬断時などに「付箋ボードでは残っているが Task ボードでは消えている」といった不整合（サイレントエラー）が生じる懸念があります。
* **改善案**:
  Board System 側の既存日次バッチ（`run_8am` 等）を活用し、定期的に `wl-sticky-note` の全件データと PostgreSQL のデータを突き合わせる**差分照合・自動補正バッチ（Self-Healing）**を実装します。
* 🚨 **【設計上の留意点】**
  * **論理削除を用いた削除・復元ループの回避**: 一方のシステムで物理削除されたデータを「データ不在」と判定して自動復元してしまう無限ループを防ぐため、`sticky_notes` テーブル側で論理削除（`status = 'ARCHIVED'` や `deleted_at`）を管理し、照合基準とします。
  * **Source of Truth（正とするデータ）の定義**:
    * 付箋の追加・本文・色などの基本情報 ➔ **`wl-sticky-note` を正とする**
    * タスク状態（未処理 / TODAY / DONE / 完了）、期限日、担当者配布 ➔ **`board-system`（PostgreSQL）を正とする**
  * **安全な運用（Dry-run モード）**: 導入初期は自動上書き補正を行わず、不整合の検知・ログ出力のみを行う「Dry-run モード」で数日間運用し、想定外のパターンで上書きが発生しないか確認した上で有効化します。

### ③ フロントエンドコンポーネント・共通ロジックの整理

* **現状と課題**:
  `wl-sticky-note` と `board-system/frontend` の双方が独立した Next.js アプリであり、`LinkifiedText` のURLパースや期限日計算（`calcDaysLeft`）、期限バッジ（`DueDateBadge`）などのロジックが個別に二重実装されています。
* **改善案**:
  単一リポジトリ内（モノリポ構造）の利点を活かし、共通ライブラリディレクトリ（例: `packages/shared` または `shared/`）を新設してロジックを集約します。
* 🚨 **【設計上の留意点】**
  * **構成の割り切り（純粋関数の徹底）**: `wl-sticky-note` は JavaScript + CSS Modules、`board-system` は TypeScript + Tailwind CSS という差異があります。UI コンポーネント自体の共有は避け、**「純粋なロジック関数」と「TypeScriptの型定義」**に絞って共通化します。
  * **パスエイリアス設定**: `wl-sticky-note` 側から TypeScript の共通モジュールを解決できるよう、`jsconfig.json`（または `tsconfig.json`）にパスエイリアスを設定します。

    ```json
    {
      "compilerOptions": {
        "paths": {
          "@shared/*": ["../../shared/*"]
        }
      }
    }
    ```

### ④ E2Eテスト・統合テストの追加

* **現状と課題**:
  バックエンドやデスクトップアプリには一部単体テストが存在しますが、システムを横断したコアフローの自動テストが存在せず、機能拡張時のデグレ確認が手動に依存しています。
* **改善案**:
  Playwright 等の E2E テストフレームワークを導入し、ユーザーの視点に立った主要なシステム間連動シナリオを自動で検証する仕組みを構築します。
* 🚨 **【設計上の留意点】**
  * **テスト環境の完全分離**: E2Eテストによって開発・本番 DB が汚染されないよう、`docker-compose.test.yml` などを導入し、テスト専用の独立した DB コンテナとポートで検証を行う構成とします。
  * **LLM（Ollama）応答の非決定性排除**: 実際の LLM を叩くとテストが不安定（Flaky）になるため、バックエンドに `MOCK_AI=true` などのテスト用フラグを設け、固定の判定結果（例: `{"is_task": true, "urgency": 80}`）を返すモック環境でテストを実行します。
  * **主要カバレッジ**: 優先すべき自動化シナリオは以下の2点です。
    1. `board-system` で付箋作成 ➔ `MOCK_AI` による Task ボード特定列への配置 ➔ `wl-sticky-note` への反映。
    2. Personal ボードでの DONE 移動 ➔ Task ボード側「完了 (5)」への非同期連動。

## 3. 実装ロードマップ（段階的アプローチ）

費用対効果（ROI）とシステムへの影響度を考慮し、以下の3フェーズで段階的に導入します。

### Phase 1: 即効性の高い同期補正とロジック共通化

1. **差分照合バッチの導入 (②)**: `board-system` の日次スケジューラを拡張し、付箋ボードのデータと DB を比較して不整合を検知・修復するフェイルセーフロジックを実装（Dry-run モードでログ確認から開始）。
2. **純粋関数の共通化 (③)**: `LinkifiedText` のパースロジックや `calcDaysLeft` 等を共通モジュール（`shared/`）に抽出し、各プロジェクトからパスエイリアス経由で import して利用する形へリファクタリング。

### Phase 2: 自動テストによる品質固定

1. **MOCK 環境とテストインフラの整備 (④)**: テスト用 DB コンテナ構成と、バックエンドの AI モック機能（`MOCK_AI=true`）を実装。
2. **E2Eテストの構築 (④)**: Playwright を用いて、「付箋作成 ➔ AI仕分け配置」および「Personal DONE ➔ Task 完了連動」の基本シナリオを自動化。

### Phase 3: データストアの統合

1. **wl-sticky-note の PostgreSQL 対応 (①)**: Node.js 側の ORM（Prismaの pull 運用）設定、および `canvas_lines` 等の追加スキーマ構築。ドラッグ中座標のインメモリ最適化も合わせて実装。
2. **データマイグレーション**: 既存の `boards.json` から PostgreSQL へデータを安全に移行するスクリプトの実装と、無停止での切り替え（Blue/Green デプロイメントの活用）。
