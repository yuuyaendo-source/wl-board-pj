# 改善計画13：複数チーム所属（N:M）対応および管理操作のパスワード保護実装プラン

## 1. 概要・影響範囲

現状のシステムでは、ユーザーは1つのチームにしか所属できず、またユーザーやチームの管理操作（追加・編集・削除）が誰でも実行可能な状態です。本計画では、以下の2点の改善を実施します。

1. **複数チーム所属（N:M化）**: 現状の `users.team_id` による1:Nリレーションを解消し、中間テーブル `user_teams` を導入して、1人のユーザーが複数のチームに所属できるようにします。
2. **管理操作のパスワード保護**: システム管理やユーザー/チームの変更・削除といった重要な操作に対し、パスワードによる管理者認証を導入し、セキュリティを強化します。

---

## 2. 影響コンポーネントと変更概要

| 対象領域 | 現状の課題 | 変更内容 |
| :--- | :--- | :--- |
| **DB / Migration** | `users` テーブルに単一の `team_id` | 中間テーブル `user_teams` の作成、および既存データの移行マイグレーション |
| **Backend Model** | `User.team_id` (1:N) | `User.teams` / `Team.users` の多対多 (N:M) リレーション設定、**後方互換用プロパティの保持** |
| **Backend Routers** | 認証なし / 単一 `team_id` 処理 | 管理系エンドポイントへの認証（Dependency）追加、複数 `team_ids` 処理への対応 |
| **Frontend UI** | 単一チーム選択 / 管理機能が無制限 | チーム選択の複数チェックボックス化、管理パスワード認証モーダルの導入、**401・UI制御ハンドリングの追加** |

---

## 3. 具体的な実装仕様

### ① 複数チーム所属対応 (N:M)

* **データベース設計 & Alembicマイグレーション (`backend/alembic/versions/`)**
  * 新しいマイグレーションスクリプトを作成し、中間テーブル `user_teams` を定義します。
    * **インデックス設定**: `(user_id, team_id)` の複合主キーに加え、チームからユーザーを逆引きするクエリ（`copy_to_team` 等）のパフォーマンス向上のため、`team_id` カラム単独でのインデックス作成（または複合主キーの順序を考慮）を行います。
    ```python
    op.create_table(
        "user_teams",
        sa.Column("user_id", sa.Integer(), sa.ForeignKey("users.id", ondelete="CASCADE"), primary_key=True),
        sa.Column("team_id", sa.Integer(), sa.ForeignKey("teams.id", ondelete="CASCADE"), primary_key=True),
    )
    op.create_index("ix_user_teams_team_id", "user_teams", ["team_id"])
    ```
  * データ移行ロジック：既存の `users.team_id` に値が存在する場合、そのデータを `user_teams` テーブルへ移行します。
  * スキーマ整理：データ移行完了後、`users` テーブルから `team_id` カラムおよび関連する外部キー制約を削除します。

* **バックエンドモデル・スキーマ改修**
  * `backend/app/models/user.py` および `backend/app/models/team.py`:
    `user_teams` テーブルを `secondary` に指定した多対多リレーションシップを定義します。
  * `backend/app/schemas/user.py`:
    `UserCreate`, `UserUpdate`, `UserResponse` スキーマのプロパティを、単一の `team_id: int | None` から、リスト形式の `team_ids: list[int] = []` および `teams: list[TeamResponse] = []` に更新します。
  * **後方互換性の確保**:
    `wl_desktop_app` や `wl-sticky-note` など他クライアントでの影響を最小限にするため、当面の移行期間として `UserResponse` に `team_id: int | None`（`team_ids` の最初の要素、または Null）をオプショナルプロパティとして残す処置を行います。

* **APIロジック改修 (`backend/app/routers/`)**
  * `users.py`: ユーザー作成・更新エンドポイントで `team_ids` を受け取り、中間テーブルの関連付けを同期・更新するロジックに変更します。**チーム未所属（`team_ids: []`）も許容し、正常に動作するよう仕様を明記・担保します。**
  * `sticky_notes.py` (`copy_to_team` エンドポイント):
    指定したチームに所属する全ユーザーを取得するクエリを、中間テーブルを使用した結合クエリ（例: `User.teams.any(Team.id == body.team_id)`）に変更します。

* **フロントエンド改修 (`frontend/app/`)**
  * `lib/types.ts`: `User` インターフェースのプロパティを `team_ids?: number[]` および `teams?: Team[]` へ更新します。
  * `components/AddUserMenu.tsx`:
    * メンバー追加・編集フォーム内のチーム選択UIを、単一選択のドロップダウンから複数選択可能なチェックボックスのリストへ変更します。
    * ユーザーリストの表示領域で、そのユーザーが所属する「すべてのチーム」のバッジが表示されるように改修します。チーム未所属時のUI表示も考慮します。

### ② 管理操作のパスワード保護

* **セキュリティ・環境変数の設定 (`backend/app/config.py`)**
  * システム設定として `admin_password: str = Field(default="admin123")` を定義します。
  * **警告ログ**: 本番稼働時（デフォルト値のままの場合）、起動時に警告ログを出力し、強力なパスワードへの変更を促します。`.env.example` の記載も更新します。

* **バックエンド認証機能の実装 (`backend/app/routers/`)**
  * **ログインAPI**: パスワードを照合し、認証トークンを発行する `POST /admin/login` を作成します。
  * **トークン管理**:
    * JWTを使用し、有効期限（`exp`）を **8時間〜24時間** など明確に設定します。
  * **FastAPI Dependencyの導入**:
    リクエストヘッダーのトークンを検証（有効期限チェック含む）する `get_current_admin` Dependencyを実装し、以下のエンドポイントを保護します。
    * LLM設定: `GET /admin/llm`, `PUT /admin/llm`
    * チーム管理: `POST /teams`, `PATCH /teams/{id}`, `DELETE /teams/{id}`
    * ユーザー管理: `POST /users`, `PATCH /users/{id}`, `DELETE /users/{id}`

* **フロントエンド UI/UXと認証ハンドリング (`frontend/app/`)**
  * **認証状態の保持**: 管理権限のセッションとして、ブラウザを閉じるまで有効な **`sessionStorage`** を採用し、不用意な権限の永続化を防ぎます。
  * **APIインターセプターと401ハンドリング (`lib/api.ts`)**:
    * 各リクエストに `Authorization` ヘッダーを自動付与。
    * トークン期限切れ等でAPIから `401 Unauthorized` が返却された際、自動的にローカルのトークンを破棄し、再認証モーダルを表示する共通エラーハンドリングを導入します。
  * **モーダル制御の競合対策**:
    * 未認証状態で「ユーザー削除」や「チーム削除」等の破壊的操作を試みた際、**先に認証モーダルを表示**し、認証完了後に本来の削除確認ダイアログを表示する（または、未認証時は削除ボタン自体を非活性/ロック表示にする）よう順序・UIを制御し、画面の破綻を防ぎます。

## 4. 検証計画

### 複数チーム所属テスト
1. **ユーザー設定**: 1人のユーザー（例: 浅川）を「ネットワーク」と「構築」の2つのチームに所属させる。チーム未所属のユーザーも作成する。
2. **チームへのコピー（1つ目）**: タスクボードで「ネットワーク」チームに対して付箋をコピーし、当該ユーザーのパーソナルボードに付箋が追加されることを確認する。
3. **チームへのコピー（2つ目）**: 同じ付箋または別の付箋を「構築」チームへコピーした際も、当該ユーザーのパーソナルボードに正しく付箋が追加されること（重複不整合がないこと）を確認する。
4. **互換性テスト**: `UserResponse` を利用する他クライアント（Desktopアプリ等）でエラーが起きないことを確認する。

### 管理操作の認証テスト
1. **未認証アクセスとUIロック**: 未認証状態での各種破壊的操作ボタンがロックされるか、またはクリック時に認証モーダルが正しく割り込むことを確認する。ダイアログの競合（確認と認証が同時に出る等）が発生しないことを確認する。
2. **認証フロー**: 正しいパスワードで認証完了後、トークンが `sessionStorage` に保存されることを確認する。
3. **認証後アクセス**: 認証完了後、各種管理操作（ユーザー追加、LLM設定変更など）が正常に実行できることを確認する。
4. **トークン失効と再認証**: 有効期限切れ（意図的に不正なトークンをセット等）の状態でAPIを呼び出した際、`401`エラーが捕捉され、自動で認証モーダルが表示されることを確認する。
