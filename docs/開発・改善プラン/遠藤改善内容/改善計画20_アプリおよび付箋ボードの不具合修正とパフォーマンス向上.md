# 改善計画20：アプリおよびボードシステムの不具合修正とパフォーマンス改善 (更新版)

## 1. 概要・目的

本計画は、ユーザーから報告された以下の5つの主要な課題について、根本原因を特定し、解決策を提示するものです。

1. パーソナルボードからの投稿が全体タスクボードに振り分けられてしまう（パーソナルアイコンがつかない）
2. ゴミ箱に入れたタスクが復活してしまう
3. デスクトップアプリの通知が出ない
4. アプリ起動のたびにタスクトレイやミニポートが増殖する（多重起動）
5. 付箋の移動（ドラッグ）がもたつく

---

## 2. 課題別の原因特定と改善アプローチ

### 課題1：パーソナルボードからの投稿が全体タスクボードに振り分けられ、アイコンがつかない

* **原因の特定**:
  パーソナルボードから投稿された付箋は、`POST /create_personal` API を経由するため、本来は AIの自動振り分け (`process_new_note_ai`) の対象外となり、タスクボードには配置されません。
  しかし、この付箋が「付箋ボード（wl-sticky-note）」へ自動同期された後、付箋ボード側の定期ポーリング等によって **`POST /api/sticky_notes`** などが呼び出されて同期バックが発生した際、新規付箋として扱われ `process_new_note_ai` が走ってしまい、結果的に全体タスクボード（TASK）へ配置されています。双方向同期システム特有の盲点によるものです。
* **改善計画**:
  1. **パーソナル専用フラグの導入 (DB変更)**: Alembicマイグレーションにより、`sticky_notes` テーブルに `is_personal_only` (BOOLEAN, デフォルト FALSE) カラムを追加し、付箋ボードとの同期・再取り込み時にもこの属性を維持します。
  2. **付箋ボード側の追従とスキーマ拡張**: デスクトップアプリのミニポートやパーソナルボードから送信されるペイロードにフラグを含めるだけでなく、**付箋ボード（wl-sticky-note）側の `server.js` およびフロントエンドのスキーマ、データストア（`boards.json`）、Socket.IOでの通信ペイロード内でも確実にこのフラグを維持**できるようにアップデートします。これにより再同期時の判定欠落リスクを防ぎます。
  3. **AI振り分けのガード強化**: `import_from_postit` や `POST /api/sticky_notes` エンドポイントにて、`is_personal_only` フラグが `True` の付箋については `process_new_note_ai` の実行および `TASK` ボードへの自動追加を完全にスキップさせるガードを挿入します。

### 課題2：ゴミ箱に入れたタスクが復活してしまう

* **原因の特定**:
  パーソナルボード上でタスク由来（`isFromTask=true`）の付箋をゴミ箱にドロップした際、フロントエンドは `api.boardPlacements.delete` を呼び出し、**パーソナルボード上の自分の配置情報のみを削除**しています。
  これにより、付箋の実体と「全体タスクボード上の配置」はそのまま残るため、タスクボード上では「未引き取り（黄色）」の付箋として再び表示されます。その後、タスクローテーション処理によって再びパーソナルの INBOX 等に割り当てられたり、タスクボードで自身が再発見したりすることで「タスクが復活した」と認識されています。
* **改善計画**:
  1. **ゴミ箱ドロップ時の仕様変更 (専用アーカイブAPIの実装)**: フロントエンド側からの単なる配置削除ではなく、バックエンドに専用のアーカイブAPI（例: `POST /api/personal/trash`）を用意します。このAPI内でトランザクションを張り、「パーソナル上の配置削除」と「タスクボード側のステータス更新」をアトミックに実行することで、状態の不整合を安全に防ぎます。
  2. **メンタルモデルの整合性検討**: ユーザーの「ゴミ箱（捨てる）」というアクションが、単なる「完了（matrix_quadrant = 5）」なのか、「不要なものとして破棄・キャンセル」なのかを検討します。UI上でゴミ箱を「完了ボックス」として見せるか、バックエンド側でタスクボード上でも「完了」とは別ステータス（アーカイブまたは削除）として扱うか、設計を洗練させます。

### 課題3：デスクトップアプリの通知が出ない

* **原因の特定**:
  Windowsデスクトップアプリでのトースト通知に `winotify` を使用していますが、以下の原因で表示に失敗、または表示が隠れるケースがあります。
  * ユーザーがWindowsの集中モード（応答不可モード）を有効にしている。
  * PowerShellの実行ポリシーやセキュリティソフトによる `winotify` のブロック。
* **改善計画**:
  1. **フォールバック通知（自前UI）の実装**: `winotify` の実行が失敗した場合や、OSによって通知がブロックされる環境を考慮し、`customtkinter` (`CTkToplevel`) などを利用したアプリ独自のフローティング・トーストウィンドウをフォールバックとして確実な解決策を導入します。
  2. **OSフォーカスの考慮とスレッドセーフ化**: 表示の際は、ユーザーの入力操作を妨げないよう `-topmost` プロパティや Windows固有の `attributes("-toolwindow", True)` などの工夫を取り入れ、フォーカス奪取を無効化 (`takefocus=False`) します。
  3. **スタッキング（積み上げ表示）の排他制御**: 複数のお知らせが連続で発生した場合に備え、自前トーストが同じ座標に重なって表示されないよう、古いトーストを自動で閉じてから新しいものを出す排他制御、またはスタッキング制御を導入し、より洗練されたUXにします。

### 課題4：ショートカットから起動するたびに起動アプリが増える（多重起動）

* **原因の特定**:
  二重起動防止ロジックにおいて、`127.0.0.1`（ローカルループバック）への TCP `connect_ex` および複数ポートのバインドを利用していますが、一部のセキュリティソフトやファイアウォール設定下ではループバック通信のプローブが遮断され、`connect_ex` が常に失敗します。その結果、先発プロセスの存在を検知できず多重起動を許容してしまっています。
* **改善計画**:
  1. **排他制御方式の変更 (ファイルロック方式)**: ネットワーク通信の遮断影響を受けやすいソケット方式を廃止します。
  2. **ロックファイルと `msvcrt` の実装**: Windows環境において、`%LOCALAPPDATA%\WonderLink pp.lock` 等の排他制御用の「ロックファイル」を作成します。Python標準の `msvcrt.locking` を利用してファイルハンドルを独占（排他）ロックすることで、確実な排他制御を実現します。
  3. **残留ロックファイルのハンドリング**: アプリの強制終了時などでロックファイル自体がディスクに残り続けた場合でも安全に起動できるよう、「起動時にロック取得処理を行い、ファイルが存在していてもロックが取得できれば、以前のゴミファイルなので上書きして続行する」というハンドリングを確実に実装します。

### 課題5：付箋の移動がスムーズじゃない

* **原因の特定**:
  付箋ボード（`wl-sticky-note`）のフロントエンド（`StickyNote.js`）において、付箋のドラッグ処理（`mousemove` / `touchmove` イベント）のたびに親コンポーネントへコールバックを発火させ、Reactの `setNotes` で全体の状態を更新しています。これにより毎ピクセルの移動ごとにボード全体の再レンダリングが発生し、カクつきが生じています。
* **改善計画**:
  1. **ドラッグ中のDOM直接操作 (`useRef`の活用)**: `wl-sticky-note` の `StickyNote.js` 内で、Reactの `useRef` を用いてDOM要素への参照を保持します。ドラッグ中はReactステート更新を呼ばず、`noteRef.current.style.transform = ...` にてインラインスタイルを直接操作して表示座標のみを更新します。
  2. **ステート更新の遅延（同期の最適化）**: サーバーへの位置情報送信およびReactステートの同期は、ドラッグ終了時（`mouseup` / `touchend`）に到達座標をまとめて一回だけ行うよう切り替えます。
  3. **リアルタイム性の考慮（必要に応じた追加設計）**: もし複数人でのリアルタイム性を重視する場合は、ドラッグ中も `requestAnimationFrame` やスロットル（例: 200ms間隔）を使って、ReactのStateを更新せずに Socket.IO で座標だけを送信する設計の追加も検討します。

## 3. 改善実施の優先度

| 優先度 | 課題 | 修正対象コンポーネント | 影響度・導入効果 |
| :--- | :--- | :--- | :--- |
| **高** | **課題5 (ドラッグのもたつき)** | `wl-sticky-note` (`StickyNote.js`) | 付箋操作のレスポンスが劇的に向上（体感速度に直結） |
| **高** | **課題2 (タスクの復活)** | `frontend` (`PersonalBoardView.tsx`) / `backend` | タスク状態管理の不整合とユーザーのストレスを解消 |
| **高** | **課題4 (アプリ多重起動)** | `wl_desktop_app` (`app.py`) | アプリ常駐の安定化、リソース浪費の防止 |
| **中** | **課題1 (ボード振り分けの不具合)** | `backend` / `wl-sticky-note` | DBスキーマ追加と同期ガードによる意図しないタスク化の防止 |
| **中** | **課題3 (通知が出ない問題)** | `wl_desktop_app` (`notifications.py`) | 環境依存の通知漏れ防止・UX改善 |

## 4. 実行手順（ロードマップ）

### フェーズ 1：基礎固めとパフォーマンス改善（最優先）

1. **課題5の修正**：`wl-sticky-note`のドラッグ処理を最適化し、`mousemove`イベントでのサーバー通信を停止。`useRef` を用いた直接DOM操作へ移行し、`mouseup` でバッチ送信する。（必要に応じてスロットル通信を導入）
2. **課題4の修正**：`wl_desktop_app`の多重起動防止をネットワーク方式から `msvcrt.locking` を用いたファイルロック方式へ変更し、ゴミファイルのハンドリングを追加する。

### フェーズ 2：データ整合性の回復と通知の安定化

1. **課題2の修正**：ゴミ箱ドロップ時にバックエンドの専用API（例: `/api/personal/trash`）を呼び出し、トランザクションを利用してアトミックにステータス変更とパーソナル配置削除を実行。UIの表現（アーカイブ等）に合わせてロジックを調整する。
2. **課題1の修正**：DBのスキーマに `is_personal_only` を追加し、APIを拡張。さらに **`wl-sticky-note` 側の `server.js` および通信ペイロード、データストアでもフラグを維持**するように改修。AI振り分けロジックにチェックを追加してタスク化を禁止するガードを挿入。
3. **課題3の修正**：`winotify`失敗時のフォールバック通知（`customtkinter`利用し、フォーカスを奪わない設定を追加）を実装。連続発生時の排他制御（スタッキング制御）も合わせて実装。

### フェーズ 3：統合テストとデプロイ

1. 各機能が互いに干渉しないか、既存の同期フローに問題が発生しないかの統合テストを実施。
2. テスト完了後、各パッケージをリリース。
