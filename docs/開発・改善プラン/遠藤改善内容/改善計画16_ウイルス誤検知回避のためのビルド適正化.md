# 改善計画16：ウイルス誤検知（Bearfoos.A!ml）回避のためのビルド・配布方式適正化

## 1. 概要・目的

Windows Defender 等のセキュリティソフトにおいて、開発・配布中のデスクトップアプリ（`WonderLinko.exe`）が「`Trojan:Win32/Bearfoos.A!ml`」等のヒューリスティック（機械学習）検知によってトロイの木馬として誤検知・ブロックされる問題を、**ビルドツールおよび配布形式のアプローチから根本的に解決**します。

これまでのソースコードレベルの対策（改善計画14、15）に加え、ビルド成果物そのものがマルウェアと見なされやすい構造（単一ファイル実行、既知のブートローダーの使用）を排除し、安全に社内展開できる状態を確立します。

---

## 2. 誤検知の根本原因（現状の課題）

1. **PyInstallerの単一ファイル化（`--onefile`）による展開挙動**
   `build_exe.ps1` で使用されている `--onefile` オプションは、アプリ起動時に一時フォルダ（`%TEMP%` 等）へDLLやスクリプト群を自己解凍・展開してから実行します。この振る舞いは「ドロッパー」と呼ばれるマルウェアの手口と完全に一致するため、最も誤検知を招きやすい構造です。
2. **標準配布ブートローダーのシグネチャの汚染**
   PyInstallerを使用し続ける場合、標準で配布（`pip install`）されているビルド済みブートローダーが組み込まれます。この標準ブートローダーは世界中の悪質マルウェア作成者にも多用されているため、バイナリのハッシュ値自体がセキュリティベンダーのブラックリストに登録されやすくなっています。
3. **署名なしバイナリによる信用スコアの低下**
   生成されたバイナリファイルにデジタル署名が付与されていないため、Windows SmartScreenや各セキュリティソフトによる「提供元不明」としての警告・ブロック対象となりやすい状態です。

---

## 3. 具体的な実装仕様 (Proposed Changes)

### ① cx_Freeze への完全移行とMSI配布への一本化（強く推奨）

PyInstaller の継続利用は C++ ビルドツールの事前インストール要求（自前コンパイル時）など、開発・運用コストの増大を招きます。既に社内ポリシーに準拠し、誤検知要素（`pynput` 等）の排除ロジックが組み込まれている `cx_Freeze` （`build_msi.ps1`）を標準ビルドツールとし、運用をMSI配布へ完全に一本化します。

* **`build_msi.ps1` を標準の配布パッケージビルドとして採用**:
  * 実行時に自己解凍を行う仕組みを持たない、安全なディレクトリ配置型（`--onedir` 相当）でインストールされるため、誤検知対策として最も優れています。
* **PyInstaller（`build_exe.ps1`）のフェードアウト**:
  * 基本的に利用を非推奨とし、可能であればプロジェクトから削除またはアーカイブします。

### ② `--onefile` オプションの廃止（PyInstallerを一時的に残す場合）

移行期間中などで `build_exe.ps1` を使用し続ける場合は、実行時に自己解凍を行う仕組みを撤廃し、ディレクトリ配置型（`--onedir`相当）へ移行します。

* **`build_exe.ps1` の改修**:
  * CLIでのビルドコマンドから `--onefile` オプションを削除します。
  * オプション削除により出力先が `dist\` 直下から `dist\WonderLinko\` （サブディレクトリ）に変わるため、ビルド後の `config.json` や `.env.example` のコピー先パスも合わせて修正します。（`config_loader.py` の `_BASE_DIR` 参照ロジックと合致します）
* **`WonderLinko.spec` の扱いと `.gitignore` の修正**:
  * 出力形式を単一ファイルからディレクトリ出力（`COLLECT` を使用する構成）へ修正します。
  * 現在 `.gitignore` で `*.spec` が除外されているため、チームで共有・管理する場合は除外設定を解除し、コミット対象に含めます。

### ③ ブートローダーの自前コンパイル（PyInstaller継続時の非推奨オプション）

PyInstallerを継続利用する場合の最終手段として、ブートローダーのシグネチャ検知を回避します。

* `pip install -q --no-binary pyinstaller pyinstaller` を用いてローカルのC++コンパイラでビルドさせます。ただし、開発環境構築のハードルが上がるため推奨しません。

## 5. 検証および運用計画 (Verification & Operation Plan)

### 実装とビルド環境の確認

1. **MSIビルドの動作確認（主軸）**:
   `build_msi.ps1` を実行し、依存関係（PIL、Socket.IO等）が正しくバンドルされ、`pynput` 等の除外指定が機能していることを確認する。
2. **`--onefile` 廃止とファイル配置の動作確認（PyInstaller残存時）**:
   `build_exe.ps1` を実行し、単一のexeではなく `dist\WonderLinko\` ディレクトリに出力されること、および `config.json` 等が同ディレクトリに正しくコピーされ、アプリが正常起動することを確認する。

### 手動動作検証とセキュリティスキャン

1. **Windows Defender によるスキャン検証**:
   `build_msi.ps1` で生成したMSI（およびディレクトリ出力されたexe群）をスキャンし、`Trojan:Win32/Bearfoos.A!ml` 等の検知が発生しないことを確認する。
2. **実行時の動作確認**:
   インストール後のアプリを起動し、起動時に `%TEMP%` フォルダ直下へ大量の一時ファイルが展開されないこと（展開によるフリーズや遅延がないこと）を確認する。
3. **アプリ内自動更新（Update Checker）の動作確認**:
   MSI化に伴い、アプリ内からのアップデート処理が正しくインストーラー（MSI）を起動し、新バージョンへの上書きインストールが完了するか検証する。

### 運用計画（社内展開・アナウンス）

1. **旧exe版ユーザーへの移行アナウンス**:
   既存ユーザーに対して、古い `WonderLinko.exe` を手動で削除し、新しい MSI 形式でインストールし直すようにアナウンスを行う。
2. **SmartScreen警告の回避・運用マニュアル化**:
   コード署名が完了するまでの暫定対応として、インストール時に表示される可能性が高い Windows SmartScreen（青い警告画面）について、「詳細情報」から実行を許可する手順をマニュアル化し、ユーザーへ事前共有する。

## 6. 将来的な検討事項・技術的アドバイス（補足メモ）

* **コード署名（SignTool）の導入（優先度：高）**:
  バイナリの構造変更（`--onedir` や `cx_Freeze` への移行）だけでは、ファイルが「未署名」である事実は変わらないため、SmartScreen 等で「提供元不明のアプリ」として警告が出るリスクが残ります。特にMSI配布へ一本化するとユーザーからの問い合わせが増加する可能性があるため、**早期（次期フェーズなど）に社内認証機関（CA）で発行したコード署名証明書、あるいは信頼されたパブリック証明書を用い、ビルドプロセスに `signtool.exe` による署名ステップを追加することを強く推奨します。**
* **PyInstaller自前コンパイルの負担**:
  Windows環境で `--no-binary pyinstaller` を実行するには「Visual Studio Build Tools（C++ によるデスクトップ開発）」が必須となります。開発者全員にこの環境を強いるのはコストが高いため、やはり cx_Freeze への完全移行が最も現実的な解決策です。
