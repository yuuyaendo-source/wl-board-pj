# 改善計画15：ウイルス誤検知（Bearfoos.A!ml）の抜本的対策とアーキテクチャ適正化 (改訂版)

## 1. 概要・目的

Windows Defender 等において、開発・配布中のデスクトップアプリ（`WonderLinko.exe`）が「`Trojan:Win32/Bearfoos.A!ml`」等のヒューリスティック（機械学習）検知によってトロイの木馬として誤検知・ブロックされる問題を根本的に解決します。

アンチウイルスの機械学習エンジンに「悪意のある挙動」としてスコアリングされやすい、**低レイヤ Win32 API の直接呼び出し** や **レジストリの自動起動キーへの直接書き込み**、さらに**旧式APIに依存するサードパーティライブラリ**をコードベースから完全に排除します。
また、インストールパスを `Program Files` へ変更し、それに伴う権限エラー（PermissionError）を回避するため、設定ファイルやログの出力先をユーザー領域（LocalAppData）へ適正化することで、セキュリティソフトの誤検知を回避しつつ堅牢な動作を保証します。

---

## 2. 誤検知の根本原因（現状の課題）

現状のコードベースと配布形態には、マルウェア（トロイの木馬）の振る舞いと一致する以下の特徴が揃ってしまっており、これが高い脅威スコアに繋がっています。

1. **`ctypes` 経由での低レイヤ Win32 API 直接実行**
   - `CreateMutexW` (二重起動防止)、`OpenProcess` / `WaitForSingleObject` (プロセス監視)、`MessageBoxW` (エラーダイアログ)、`RegisterHotKey` / `GetMessageW` (キーボード監視) などの直接呼び出し。
   - 未署名の Python コンパイルバイナリがこれらの API を直接呼ぶ挙動は、キーロガーやインジェクション型マルウェアと非常に強く類似していると判定されます。
2. **レジストリ（Run キー）への直接書き込みによる永続化**
   - `winreg` を使用し、自動起動キーに対して実行ファイルのパスを登録する処理が、マルウェアの永続化（Persistence）手法と誤認されています。
3. **未署名バイナリの `AppData\Local` 配下での実行**
   - ユーザー領域（AppData）で動作する未署名・未知のパッカー（cx_Freeze）バイナリは、Program Files 領域に比べて極めて厳しい評価を受けます。
4. **サードパーティライブラリとビルド時のリスク**
   - `win10toast` / `win10toast-click` 等は、内部的に古い Win32 API をフックしており、ヒューリスティック検知のトリガーになるリスクを孕んでいます。

---

## 3. 具体的な実装仕様 (Proposed Changes)

### ① `ctypes` への依存と Win32 API 呼び出しの全廃

コード内から `import ctypes` および付随する Windows API 呼び出しをすべて削除し、安全な標準ライブラリの手法へ置き換えます。

- **二重起動防止の変更 (`app.py`)**:
  `CreateMutexW` を廃止します。
  **【推奨】** 代替として、`127.0.0.1`（ローカルループバック）の特定のポートに対する **`SO_EXCLUSIVEADDRUSE` を設定したソケットポートバインド** を使用します。（ファイアウォールの警告回避のためループバックアドレスに限定）
  *(※ファイルロック方式はアプリクラッシュ時にロックファイルが残存する懸念があるため、プロセス終了時にOSが確実にポートを解放するソケット方式を強く推奨します。`SO_REUSEADDR` は二重起動を許容してしまうため使用不可)*
  **【留意点】** 他のアプリケーションとの競合を避けるため、バインドするポート番号はエフェメラルポート帯（例: 50000番台）などのマイナーな固定ポートを選定します。バインド失敗時は複数のフォールバック候補ポート（例: 50000, 50001, 50002 などをリスト化）を試行する処理を含めます。
  ロック取得失敗時（すべてのポートバインド失敗時）は、既存プロセスへ `show_request` 通知を送り、自プロセスを即座に終了させます。
  **【実装時の注意】** バインドに成功したソケットオブジェクトは、**必ずアプリ終了時（または `app.py` のグローバルスコープ）まで変数として保持し続ける**実装としてください。

- **エラーダイアログの変更 (`app.py`)**:
  起動時エラー用の `MessageBoxW` 等を完全に削除し、`tkinter.messagebox` の利用へ置き換えます。
  **【重要】** 起動時などルートウィンドウがない場合は `root = tkinter.Tk(); root.withdraw()` を実行してから呼び出し、直後にプロセスを終了させます。ただし、アプリ実行中（`_show_notification_help`など）で既にメインループが走っている場合は、新たな `Tk()` は生成せず既存のウィンドウ（`_miniport_window`等）を親として指定し、多重ルートウィンドウによるクラッシュを防ぎます。
  **【フォールバックの実装】** 万が一、環境依存などで `tkinter` 自体のロードに失敗した場合に備え、例外ハンドリング (`except` ブロック) 内では `%LOCALAPPDATA%` 内の診断ログへの追記のみを行い、ダイアログを出さずに安全に `sys.exit(1)` する（Silent Crashを許容する）堅牢なフォールバック設計とします。

- **プロセス終了待機の変更 (`app.py`)**:
  `OpenProcess` 等を削除し、`os.kill(pid, 0)` と `time.sleep()` を用いた生存チェックループのみに一本化します。
  **【実装時の注意】** 既に `app.py` 内の非Windows（`else`）ブロックで実装されている `os.kill(pid, 0)` のロジックを全OS共通として引き上げ、Windows専用の `ctypes` 呼び出しブロックを丸ごと削除する形で安全かつシンプルに実装します。

- **グローバルホットキーの廃止・仕様変更 (`mini_port.py`)**:
  `RegisterHotKey` を用いた実装を削除します。「Ctrl+Shift+Space」によるグローバル呼び出し機能を廃止し、通知領域アイコンのクリック操作等へ誘導します。

### ② スタートアップ登録（レジストリ操作）の廃止と検知回避

- **自動起動登録の適正化 (`startup.py`)**:
  `winreg` を用いたレジストリへの直接書き込みを全廃します。
  代替として、Windows の「スタートアップ」フォルダ（`shell:startup`）へのショートカットの配置・削除に変更します。プロジェクトに既に導入されている `pywin32` (`win32com.client`) を利用して、Python 側から安全に `.lnk` ファイルを動的生成・削除する設計とします。
  **※COMオブジェクトの操作は環境依存でエラーが発生する可能性があるため、必ず `try-except` で保護し、失敗時は `app_log.py` に記録してクラッシュを防ぐフェイルセーフな実装とします。**
  **【バンドル漏れの防止】** `cx_Freeze` が `win32com` 系の動的ロードを拾いきれないことを防ぐため、`setup.py` に `"win32com"`, `"win32com.shell"`, および裏で依存される `"pythoncom"` も明示的なインクルードに追加します。
- **状態判定ロジックの変更 (`startup.py`)**:
  `is_startup_enabled()` の判定ロジックをスタートアップディレクトリ内の `.lnk` ファイルの存在チェックへ差し替えます。

### ③ 依存パッケージの整理と通知機能の一本化

- **`win10toast` 系パッケージの完全排除**:
  `requirements.txt` から削除し、通知機能は `winotify` のみに一本化します。
  `setup.py` の `build_exe_options["includes"]` リストからも `"win10toast"` および `"win10toast_click"` を確実に削除します。

### ④ インストール先とパッケージング構成の変更

- **Program Files へのインストール (`setup.py`)**:
  `bdist_msi_options` の `initial_target_dir` を `[ProgramFilesFolder]` に変更し、`all_users: True` を設定して管理者権限による All Users インストールへ変更します。
  **【モジュールの明示的追加】** `build_exe_options["includes"]` または `"packages"` に `"win32com"`, `"win32com.shell"`, `"pythoncom"` を明示的に指定してバンドル漏れを防ぎます。

### ⑤ ユーザー領域（%LOCALAPPDATA%）へのファイル出力先の完全移行 🚨【重要修正】

Program Files 配下にインストールされることに伴い、アプリのベースディレクトリ（`_BASE_DIR`）への書き込みは `PermissionError` となります。書き込みが発生するすべてのファイルを `%LOCALAPPDATA%\WonderLink` 配下へ移行します。
**※各ファイルへアクセスする前に、必ず `os.makedirs(dir_path, exist_ok=True)` を実行してディレクトリの存在を保証します。**

1. **`config.json` の移行 (`config_loader.py`)**:
   - 読み書き先を `%LOCALAPPDATA%\WonderLink\config.json` に変更します。
   - **【重要】** 初回起動時のコピー処理は `shutil.copy` ではなく、**`json.load()` で元ファイルを読み込み、`json.dump()` で `%LOCALAPPDATA%` 側に書き出す実装**とします。（`shutil.copy` を使うと Program Files 側の厳しいアクセス権限(ACL)を引き継いでしまい、後の書き込みで `PermissionError` が起きるリスクがあるため、これを完全に排除します）
   - 既存の設定ファイルを誤って上書きしないよう、`%LOCALAPPDATA%` 側にファイルが **「存在しない場合のみ」** コピー処理を実行するガード条件を徹底してください。
2. **ログ出力先の適正化 (`app_log.py`)**:
   - `WonderLinko.log` の出力先パスを `%LOCALAPPDATA%\WonderLink\WonderLinko.log` へ変更します。
3. **起動時診断ログの適正化 (`app.py`)**:
   - PILロード失敗時などに出力される `WonderLinko_diagnostic.txt` の出力先を `%LOCALAPPDATA%\WonderLink\WonderLinko_diagnostic.txt` へ変更します。
   - **【重要】** 起動直後の `_write_diagnostic` 関数内で、`config_loader` を読み込む前の非常に早い段階でパス解決を行う必要があります。そのため、`os.environ.get("LOCALAPPDATA")` を用いてディレクトリを生成・書き込むよう実装を修正してください。
   - **【フォールバック追加】** 万が一 `os.environ.get("LOCALAPPDATA")` が取得できなかった場合（特殊な実行コンテキストなど）に備え、フォールバックとして `os.path.expanduser("~")` 配下などを利用するロジックを実装し、エラーによるクラッシュを防ぎます。

## 5. 検証および運用計画 (Verification & Operation Plan)

### 実装とビルドの確認

1. **コード検索**: `ctypes`, `winreg`, `SO_REUSEADDR` といったキーワードで検索を行い、不適切な呼び出しが消滅していることを確認する。
2. **ビルド検証**: `build_msi.ps1` を実行し、正常に MSI が生成されること、およびスタートアップ操作時にCOMエラーが発生しないことを確認する。

### 手動動作検証

1. **セキュリティソフトでのスキャン**:
   - ビルドされた MSI およびインストール後の `WonderLinko.exe` を Windows Defender でスキャンし、脅威が検知されないことを確認する。
2. **インストールと権限テスト**:
   - MSI 実行時に UAC プロンプトが表示され、`C:\Program Files\WonderLink\WonderLinko` にインストールされることを確認する。
   - 通常ユーザー権限でアプリを起動し、設定ファイルやログが `%LOCALAPPDATA%\WonderLink` に生成され、書き込みエラー (`PermissionError`) が発生しないことを確認する。
3. **二重起動制御の確認**:
   - アプリ起動中に追加で起動を試み、ソケットバインドによって正しくブロックされ、既存プロセスのミニポートが前面化されることを確認する。
4. **スタートアップ登録の確認**:
   - 設定画面で「PC起動時に自動で起動」の ON/OFF を切り替え、`shell:startup` フォルダにショートカットが正しく作成・削除されること、及びCOMエラーでクラッシュしないことを確認する。

### 運用上の留意点と周知事項 🚨【重要】

1. **旧バージョン（AppDataインストール版）からの移行手順**:
   - Per-User（旧版）から Per-Machine（新版）へのコンテキスト変更時、同じ MSI の `UpgradeCode` を持っていても Windows Installer が別のインストールと認識するため、自動アンインストールが失敗します。
   - **社内アナウンスにて、「必ず旧バージョンを手動でアンインストールしてから、新バージョンをインストールすること」を必須の運用フローとして周知徹底します。**
2. **アンインストール時のユーザーデータ（%LOCALAPPDATA%）の残存**:
   - アンインストールを実行しても、アプリ起動後に動的に生成される `%LOCALAPPDATA%\WonderLink` 配下のデータは残存します。完全に削除を希望するユーザーに対しては、「手動で `%LOCALAPPDATA%\WonderLink` フォルダを削除する」案内をサポート手順として整理します。
3. **グローバルホットキー（Ctrl+Shift+Space）廃止の周知**:
   - セキュリティ向上のための必須措置としてキーボードショートカットを廃止し、タスクトレイからの操作に一本化します。この UX 変更によるユーザーの混乱を防ぐため、変更理由を明記して周知します。
4. **コード署名（Code Signing）の将来的な導入検討**:
   - 本計画の実装によりヒューリスティック検知のリスクは劇的に下がりますが、「未署名バイナリである」という根本的な状態は残ります。将来的にはコード署名証明書（Code Signing Certificate）の導入を検討し、Windows Defender SmartScreen 警告などを完全にクリアにすることを推奨します。
