# バグ修正実装計画

## 概要

報告された5件のバグについて、コードを調査し原因を特定しました。以下に修正計画を示します。

---

## バグ一覧と根本原因

### バグ1: パーソナルボードで入力した内容が全体タスクボードに振り分けられる

**根本原因**: `backend/app/routers/sticky_notes.py` の `create_personal_note` エンドポイント（L233-283）が、PERSONAL 配置を作成した後に `process_new_note_ai(note.id, db)` を呼んでいる。

この `process_new_note_ai` は `orchestrator.py` の中で **TASK ボードに配置を追加する処理**（`_place_on_task_board`）を実行するため、パーソナルボードに投稿した付箋が全体タスクボードにも自動登録されてしまう。

```python
# sticky_notes.py L277-280 (問題箇所)
from app.services.orchestrator import process_new_note_ai
await process_new_note_ai(note.id, db)   # ← パーソナル投稿でも呼ばれるため TASK にも追加される
```

**修正方針**: `create_personal_note` では `process_new_note_ai` を呼ばず、AI振り分け・TASK配置をスキップする。

### バグ2: パーソナルボードのゴミ箱が使えない

**根本原因**:  `PersonalBoardView.tsx` の `PersonalTrashDropZone` コンポーネント（L291-327）を確認すると、ドロップ時に `noteId` を取得して `api.stickyNotes.delete(noteId)` を呼ぶが、`NoteCard.tsx` の drag 処理（L326-338）では `placementId` と `noteId` 両方を `dataTransfer` に設定している。

問題: `PersonalTrashDropZone.handleDrop` の L310 では:
```ts
const noteId = e.dataTransfer.getData("noteId") || e.dataTransfer.getData("placementId");
```
と書かれているが、`isFromTask` のチェック（L308）が `"true"` と文字列比較しており、これは正常。

しかし実際にドロップした際 `getData("noteId")` が**空文字になる**ことがある（ブラウザのセキュリティ制限で `dragover` 中は `getData` が空を返す）のは `dragover` 時の問題ではなく `drop` 時のはず。

コードをさらに精査すると、`LaneColumn.handleDrop`（L532-554）が `e.preventDefault()` を処理して **親コンポーネントのドロップイベントを消費してしまう**可能性がある。

実際の問題: `PersonalTrashDropZone` と `LaneColumn` が同一親要素の中に存在しないため、ドロップは正常に届くはず。

本当の問題: `handleTrashDrop` が `noteId: number` を引数にとるが、`PersonalTrashDropZone.onDrop` の型シグネチャが `(noteId: number) => void` となっている（L291）。しかし `handleTrashDrop` では `api.stickyNotes.delete(noteId)` を呼んでおり、これは **StickyNote を完全削除**する。

`delete_sticky_note` バックエンドは StickyNote を削除するが、パーソナル投稿（`postit_board_id` が null）の付箋は削除後に参照エラーが起きる可能性はない。

**改めて確認**: バグ1の修正前は、パーソナルボードで投稿した付箋が TASK ボードにも配置される。その状態では `delete_sticky_note` で StickyNote 自体を消しても TASK 配置に影響する可能性あり。ただし現在は cascade delete されるはず。

**真の原因**: `PersonalTrashDropZone` の `handleDrop` が `e.dataTransfer.getData("isFromTask")` でブロック判定しているが、パーソナル投稿の付箋でも `NoteCard` の `dragData` に `isFromTask: String(!!p.is_from_task)` を設定している。

バグ1の副作用として、パーソナル投稿した付箋がTASKボードにも配置されるため `is_from_task` が `true` になる → ゴミ箱ドロップ時に `isFromTask === "true"` のチェックでブロックされる。

**修正方針**: バグ1を修正して TASK への二重配置を防ぐ。それでもゴミ箱が使えない場合は、PERSONAL ボードのゴミ箱は `is_from_task` にかかわらず削除できるよう修正。具体的には `is_from_task` のフラグが `true` でも PERSONAL ゴミ箱へのドロップで Personal 配置のみ削除する処理に変更する。

### バグ3: タスクボードからゴミ箱に移動しても復活する

**根本原因**: `taskboard/page.tsx` の `TrashDropZone.handleDrop`（L386-391）が `noteId` を取得して `api.stickyNotes.delete(noteId)` を呼ぶ。

しかし `import_from_postit` で取り込まれた付箋は `postit_board_id` と `postit_note_id` を持つ。削除後、**5分ごとの自動取り込み**（L136-162）が再度 `importFromPostit` を呼んで同じ付箋を再インポートする。

`import_from_postit` バックエンド（`sticky_notes.py` L125-181）は `postit_board_id + postit_note_id` でユニーク判定しているが、StickyNote を削除した場合は次の自動取り込みで再作成される。

**修正方針**: 削除後に付箋ボード側（wl-sticky-note）で付箋をグレー化（アーカイブ）する処理は既にある（`_notify_postit_archive` / `delete_sticky_note`）。しかし `import_from_postit` の filter が `gray: false` の付箋のみを対象にしているため（`taskboard/page.tsx` L104: `.filter((n) => !n.gray)`）、本来はグレー化された付箋は再インポートされないはず。

問題: wl-sticky-note への通知（`_notify_postit_archive`）が失敗している可能性がある。または `postit_board_url` が設定されていない。

wl-sticky-note は `PATCH /api/boards/{board_id}/notes/{note_id}` で `{"gray": true}` を受け取るはず。

**追加確認が必要**: wl-sticky-note 側のエンドポイントを確認する必要がある。

一方で、もし wl-sticky-note との連携が機能しているなら、グレー化された付箋はフロントエンドの filter でスキップされるはず。

**より確実な修正方針**: `DELETE /sticky_notes/{note_id}` 後に TASK ボードからの refetch 時に該当付箋が消えているが、自動取り込みが再取得してしまうケース。wl-sticky-note へのグレー化通知が確実に届くように修正する（タイムアウトを延ばす、リトライを追加する）。

### バグ4: デスクトップアプリの通知が出ない

**根本原因**: `notifications.py` の `show_toast`（L99-152）は `winotify` を使用。Windows の通知設定（フォーカスアシスト等）やアプリIDの問題が考えられる。

ただし `app_id = "WonderLinko.Desktop"` はコメントに「通知オフで復旧しない場合の対策で WonderLinko.Desktop に変更」とある。

**可能性1**: Windows の通知センター設定で WonderLinko.Desktop が無効化されている。
**可能性2**: `winotify` が正しくインストールされていない。
**可能性3**: `are_enabled()` が False を返している（config の `notifications_enabled` が False）。

`_toggle_notifications` で通知を ON/OFF できるが、config が書き換わっていない状態でも `are_enabled()` が False になることがある。

**確認可能な改善**: `show_toast` の except ブロック（L146-147）が例外を握りつぶしているため、なぜ失敗しているかわからない。ログを追加する。

**修正方針**: `show_toast` の except ブロックでエラーを `log_info` に記録する。また `app_id` をユーザーが設定した表示名（または固定値）と合致させるために、Windows の登録済みアプリIDとの一致を確認。

### バグ5: デスクトップのショートカットから起動するたびにアプリが増える

**根本原因**: `app.py` の `_acquire_single_instance_lock()`（L196-224）は、127.0.0.1 の特定ポート（50050-50052）へのバインドで単一インスタンスを制御している。

**問題**: ショートカットから起動された場合、既に起動中のプロセスがある場合は `_acquire_single_instance_lock()` が `False` を返し、`_signal_existing_instance_to_show()` を呼んで `return` するはずである。

しかし **「ショートカット」が「スタートアップ」のショートカットではなく、デスクトップ上の別ショートカット（インストーラーが作成した `WonderLinko.Desktop` のピン留めアイコン）**の場合、ショートカットのターゲットが別のパスを指している可能性がある。

画像を見ると、同じアイコンが複数並んでいる。これは pystray が複数のシステムトレイアイコンを作成していることを示す。

**真の原因**: 単一インスタンスロックは取得できているのに、なぜトレイアイコンが増えるのか？  
→ `_acquire_single_instance_lock()` は 3つのポート（50050, 50051, 50052）を順番に試し、**最初に空いているポートにバインド**する。もし**3つのプロセスが起動**していれば、それぞれ別のポートにバインドして「ロック取得成功」と判断し、3つすべてのプロセスが起動してしまう。

**修正方針**: 候補ポートを1つにするか、または全候補ポートへの接続テストを行って先発プロセスの存在を確認してからバインドを試みる。具体的には：
1. まず全候補ポートに TCP 接続を試み、接続できれば先発プロセスありと判断
2. 接続できなければ、1番目のポートにバインドを試みる（他の候補は使わない）
