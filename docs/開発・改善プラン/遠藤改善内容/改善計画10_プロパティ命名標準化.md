# 改善計画10：プロパティ命名標準化とスキーマ型定義の最適化

## 1. 目的と基本方針 (Executive Summary)
* **目的**: 期限プロパティ（`dueDate` / `due_date`）の混在による各層での手動フォールバック処理（`note.dueDate || note.due_date`）を一掃し、コードの保守性と型安全性を向上させる。
* **基本方針 (アプローチA: 境界マッピング方式)**:
  * 既存の `board-system`（Backend / Frontend / Desktop）全体に広範な影響を及ぼす全プロパティの camelCase 化は避け、既存の設計規約である **`snake_case`（`due_date`）に統一**。
  * 外部/旧システムである `wl-sticky-note`（付箋サーバー）との通信境界においてのみ、Pydantic の `AliasChoices` や変換ユーティリティを用いて相互に吸収・正規化する。

---

## 2. 影響範囲の整理と対策

| システム / コンポーネント | 現状 | 変更後の設計 |
| :--- | :--- | :--- |
| **board-system/backend** | `due_date` / `dueDate` を個別処理 | `snake_case`（`due_date`）に一貫統一。受信用 Pydantic スキーマのみ `AliasChoices` で `dueDate` も許容。 |
| **board-system/frontend** | `note.dueDate || note.due_date` の二重参照 | `lib/types.ts` で `due_date?: string | null` に統一し、不要な手動フォールバックコードを削除。 |
| **wl-sticky-note** | `boards.json` に `dueDate` / `due_date` が混在 | データ読み込み時・APIレスポンス生成時に `dueDate` へ正規化し、`StickyNote.js` 等の参照を統一。 |
| **wl_desktop_app** | `item.get("due_date")` を参照 | バックエンド側の `due_date` 返却統一により、既存コードを変更せず安全に動作維持。 |

---

## 3. 具体的な実装仕様 (Proposed Changes)

### 3.1 バックエンド改修 (`board-system/backend`)
* **スキーマ受信用エイリアス設定 (`app/schemas/sticky_note.py` 等)**:
  `AliasChoices` を適用し、付箋サーバーや外部連携から `dueDate` が送られてきた場合でも自動的に `due_date` フィールドへマッピングします。

  ```python
  from pydantic import BaseModel, Field, AliasChoices

  class ImportFromPostitItem(BaseModel):
      id: str
      text: str
      due_date: str | None = Field(
          default=None,
          validation_alias=AliasChoices('due_date', 'dueDate')
      )

  class StickyNoteCreate(BaseModel):
      content: str
      author_id: int | None = None
      # ...
      due_date: str | None = Field(
          default=None,
          validation_alias=AliasChoices('due_date', 'dueDate')
      )
  ```

* **レスポンスキーの固定**:
  すべての API レスポンスで `due_date`（snake_case）を確実に返却します。

### 3.2 付箋サーバー改修 (`wl-sticky-note`)
* **データ読み込み・出力の正規化 (`src/server.js`)**:
  `boards.json` のロード時や Socket.IO イベント送信時に、プロパティを `dueDate` に正規化する処理を追加します。

  ```javascript
  function normalizeNote(note) {
    if (note.due_date !== undefined) {
      if (note.dueDate === undefined) {
        note.dueDate = note.due_date;
      }
      delete note.due_date;
    }
    return note;
  }
  ```

* **クライアントコンポーネントの修正 (`src/components/StickyNote.js` 等)**:
  `note.dueDate || note.due_date` などの判定を削除し、`note.dueDate` への直接参照に統一します。

### 3.3 フロントエンド改修 (`board-system/frontend`)
* **型定義の更新 (`lib/types.ts`)**:
  `StickyNote` や `PlacementWithNote` インターフェースの型を `due_date?: string | null` に一元化します。
* **フォールバックコードの削除 (`NoteCard.tsx`, `OneLineInput.tsx` 等)**:
  `const target = note.dueDate || note.due_date;` などの二重評価コードを全削除します。

### 3.4 デスクトップアプリ確認 (`wl_desktop_app`)
* `task_remind_dialog.py` 等の `item.get("due_date")` 処理が、バックエンドの `due_date` 統一によって正常に動作することを検証・確保します。

## 4. 段階的移行戦略 (Migration Strategy)

| フェーズ | 対象 | 内容 |
| :--- | :--- | :--- |
| **Phase 1** | Backend (Pydantic) | スキーマに `AliasChoices` を導入し、`dueDate` / `due_date` の双方を受信可能にする。 |
| **Phase 2** | Sticky Server | `wl-sticky-note` の保存・送信データを `dueDate` に正規化し、UIコンポーネントを統一。 |
| **Phase 3** | Frontend & Cleanup | `board-system/frontend` の型定義と不要な手動フォールバックコード（`||`）を完全削除。 |

## 5. 検証計画 (Verification Plan)

### 自動テスト / API テスト
* **Pydantic パース検証**: `due_date` および `dueDate` のどちらをペイロードに含めても、正しく `due_date` にパースされることを検証。

### 結合・手動検証
1. **ボード間双方向同期**: 付箋ボード（`wl-sticky-note`）で期限を設定し、タスクボードへ取り込んだ際に `due_date` が欠落せず保持されるか確認。
2. **デスクトップアプリ連動**: `wl_desktop_app` のタスクリマインドダイアログで期限が正常に読み込まれ、表示されるか確認。
3. **画面レンダリング**: Task Board、Personal Board、Meeting Board で期限バッジ（`DueDateBadge`）が正常に機能するか確認。
