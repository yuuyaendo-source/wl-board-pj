# Wonder Linko Desktop v3.0.0 リリース手順

2026-05-27 リリース。**最初の手動配布**が必要 (旧 cert 期限切れで自動更新が動かないため)。

## 何が変わったか (v2.2.2 → v3.0.0)

1. **内部ドメイン移行**: `wonder-link.co.jp` → `wonder-link.com`
   - `update_check_url` も `.com` に。旧 cert 期限切れ + 旧ドメイン廃止後でも更新が走る
2. **新アイコン**: VRM リン子から作成した 2D アイコンを assets/ に同梱
   - exe / msi / トレイ / トースト / ミニポート 全部統一
3. **features セクション**: opt-in 機能フラグ枠を追加 (全 OFF 既定)
   - `taskbar_mode` / `linko_avatar` / `visitor_notify` / `brainstorm`
4. **設定ダイアログ**: トレイ「設定...」/ ミニポート右クリック「設定...」から開く

## Windows 側でやること

### A. ビルド環境準備

- Windows PC (Python 3.12 以上)
- リポジトリを git clone (or pull で最新化)
- PowerShell 起動

### B. config.json を本番値に置き換える

```powershell
cd wl-board-pj\wl_desktop_app
Copy-Item config.production.example.json config.json -Force
notepad config.json   # `_description` を消す/必要なら手調整
```

cx_Freeze は **ビルド時の `config.json` をそのまま msi にバンドル**する。
本番 URL が入った状態でビルドすること。

### C. MSI ビルド

```powershell
cd wl-board-pj\wl_desktop_app
.\build_msi.ps1
```

出力: `dist\WonderLinko.msi`

ビルドスクリプトは `cx_Freeze` / `freeze-core` を pip install したあと
`python setup.py bdist_msi` を実行する。**`_imaging*.pyd` がバンドルに
含まれていないと配布禁止** (build_msi.ps1 が自動でチェック)。

### D. ローカルで msi を確認 (推奨)

1. インストール: `dist\WonderLinko.msi` をダブルクリック
2. インストール先: `%LOCALAPPDATA%\WonderLink\WonderLinko`
3. デスクトップにできたショートカットから起動
4. トレイにリン子アイコンが出ること
5. 右クリック「設定...」で設定ダイアログが開くこと
6. トレイ「アプリをアップデート」をクリック → 「更新なし: 現在=3.0.0 最新=3.0.0」
   (= 自動更新の経路が動いている)

### E. 本番サーバに msi をアップロード + blue/green デプロイ

**重要な前提:** backend Dockerfile が `COPY . .` で `desktop_app_releases/` を
**イメージにビルド時焼き込み**している。
ホスト側のファイルを差し替えただけでは、稼働中のコンテナからは見えない。
**必ず blue/green deploy.sh を走らせてイメージを作り直す**こと。

#### E-1. ホスト側のファイルを最新化

```bash
ssh devuser01@wlboardsys-app-01
cd /var/www/wlinko-pj
git pull   # latest.json (3.0.0) と version.py bump を取得
ls -la board-system/backend/desktop_app_releases/
```

#### E-2. msi をホストに転送

```powershell
# Windows 側 (ビルド PC)
scp dist\WonderLinko.msi devuser01@wlboardsys-app-01:/var/www/wlinko-pj/board-system/backend/desktop_app_releases/WonderLinko.msi
```

ホスト側で `WonderLinko.msi` と `latest.json` が同じ desktop_app_releases/ にあることを確認。

#### E-3. blue/green デプロイ (deploy.sh)

```bash
cd /var/www/wlinko-pj/board-system
./deploy/deploy.sh
```

deploy.sh の動作:

1. 現在の active 色 (`/etc/nginx/conf.d/active_env.conf` で判定) を確認
2. **反対色のコンテナを `docker compose ... up -d --build`** で新規構築
   - この時点で新 `latest.json` / `WonderLinko.msi` がイメージに焼き込まれる
3. 新コンテナの `/health` をヘルスチェック
4. alembic migration 実行
5. `active_env.conf` を新色のポートに書き換え + `sudo systemctl reload nginx`
6. 旧色のコンテナを停止

⚠️ **やってはいけないこと:**

- `docker compose -f docker-compose.prod.yml up -d --build linko-backend-blue` を
  直接叩く → サービス名と container_name が異なるので意図しない動作になる
- ホスト側 `desktop_app_releases/latest.json` だけ書き換えて再ビルド忘れ → 反映されない

#### E-4. 反映確認

```bash
curl https://wl-ai-board.internal.wonder-link.com/api/bs/desktop-app/latest.json
# → 新 version が返ってくる

# コンテナ内も確認
NEW_BACKEND=$(docker ps --format '{{.Names}}' | grep "^linko-backend-")
docker exec "$NEW_BACKEND" cat /app/desktop_app_releases/latest.json

# msi も配信されているか
curl -sI https://wl-ai-board.internal.wonder-link.com/api/bs/desktop-app/WonderLinko.msi | head -3
# → 200 OK
```

#### E-5. (Tips) build cache に注意

`COPY . .` が `CACHED` のまま走ると、新 `latest.json` がイメージに入らないことがある。
deploy.sh で `desktop_app_releases/` の中身変更だけだと cache 判定が曖昧になる場合があるので、
反映されない症状が出たら `--no-cache` で backend を再ビルド:

```bash
cd /var/www/wlinko-pj/board-system
docker compose -f docker-compose.prod.yml -p board-system-blue build --no-cache backend
docker compose -f docker-compose.prod.yml -p board-system-blue up -d backend
```

## v3.0.1 (auto-update 初回実証)

クリック起動のたびにミニポート/トレイが増殖するバグを修正。**この版は手動配布せず、
v3.0.0 端末の自動更新で配布**することで auto-update 経路を初めて実証する。

修正内容:

- Windows named mutex (`Local\\WonderLinkoDesktopAppSingleInstance`) で単一インスタンス
  保証
- 重複起動を検知したら `%LOCALAPPDATA%\\WonderLink\\show_request` を作成して自プロセス
  終了。先発プロセスは 1 秒ごとにこのファイルを監視し、検出したらミニポートを前面化

ビルド & 配布手順は下記「次回以降のリリース手順」と同じ。

## 次回以降のリリース手順 (v3.0.1+)

旧ドメイン期限切れ問題はもう無いので、**手動配布は今回限り**。今後は次の 7 ステップ:

### 1. 開発側 (dev WSL)

```bash
# (a) コード変更を commit
git add ...
git commit -m "..."

# (b) version.py bump (例 3.0.0 → 3.0.1)
sed -i 's/__version__ = "3\.0\.0"/__version__ = "3.0.1"/' wl_desktop_app/version.py

# (c) latest.json を同じ version に更新
sed -i 's/"version": "3\.0\.0"/"version": "3.0.1"/' board-system/backend/desktop_app_releases/latest.json

# (d) commit & push
git add wl_desktop_app/version.py board-system/backend/desktop_app_releases/latest.json
git commit -m "release(desktop): vX.Y.Z bump"
git push origin main
```

### 2. Windows ビルド PC

```powershell
cd path\to\wl-board-pj
git pull

cd wl_desktop_app
# v3.1.4 以降: config.json は msi にバンドルしない設計のため、
# Copy-Item config.production.example.json config.json -Force は **不要**。
# defaults が本番 URL になっているので、ビルド前の追加作業なし。

.\build_msi.ps1
# 出力: dist\WonderLinko.msi
```

### 3. msi を本番サーバへ転送

**運用ルール**: ロールバック用に過去版を残せるよう、サーバ上では **バージョン付き** ファイル名で配置する。
`latest.json` の `url` も同じファイル名を指すこと。

```powershell
# バージョン付き名 (例: 3.1.0) で配置
scp dist\WonderLinko.msi devuser01@wlboardsys-app-01:/var/www/wlinko-pj/board-system/backend/desktop_app_releases/WonderLinko_3.1.0.msi
```

そして dev リポジトリの `latest.json` の `url` も同じファイル名にして commit + push:

```json
{
  "version": "3.1.0",
  "url": "https://wl-ai-board.internal.wonder-link.com/api/bs/desktop-app/WonderLinko_3.1.0.msi"
}
```

⚠️ ファイル名と `latest.json` の `url` が一致していないと、クライアントは 404 を受けて
**「更新あり」のトーストは出るがダウンロードに失敗してインストールが走らない**。

### 4. 本番サーバで git pull

```bash
ssh devuser01@wlboardsys-app-01
cd /var/www/wlinko-pj
git pull   # latest.json bump を取得
```

### 5. 反映 (v3.2.3 以降: bind mount 化で deploy.sh 不要)

`desktop_app_releases/` は backend コンテナに bind mount されているので、
手順 3 (scp) + 手順 4 (git pull で latest.json 更新) だけで **即反映**。
deploy.sh は不要 (frontend/backend のコード変更時のみ実行)。

```bash
# 通常は何もしなくてよい。確認だけ:
curl https://wl-ai-board.internal.wonder-link.com/api/bs/desktop-app/latest.json
```

⚠️ bind mount を初めて有効化するときだけ、1 度 `./deploy/deploy.sh`
(または `docker compose ... up -d`) で compose 変更を反映すること。

### 6. 反映確認

```bash
curl https://wl-ai-board.internal.wonder-link.com/api/bs/desktop-app/latest.json
# 新 version が返れば成功
```

### 7. ユーザー側

- 何もしなくて OK。次回アプリ起動時に自動チェック → アップデート
- 「すぐ反映したい」なら、トレイ → 「アプリをアップデート」を手動クリック
- v3.0.1 以降は単一インスタンス制御により、クリック連打しても増殖しない

## 共通の落とし穴

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| ホストの `latest.json` を更新したのに `curl` で旧 version が返る | backend Dockerfile が `COPY . .` でイメージにファイルを焼き込んでいるため、コンテナ再ビルド前は反映されない | `./deploy/deploy.sh` を走らせる (本書 E-3) |
| deploy.sh が `Health check failed` で落ちる | 新コンテナの 8010 or 8020 が他プロセスに占有 / DB が落ちている | `docker ps` で他のコンテナを確認・整理 (空サフィックスのゴミコンテナ等) |
| `docker compose ... up -d --build linko-backend-blue` を直接叩いて反映されない | サービス名は `backend`、container_name は `linko-backend-${COLOR}`。サービス名で指定するか deploy.sh を使う | `./deploy/deploy.sh` を使う |
| deploy.sh のビルドで `COPY . .` が CACHED されて新 latest.json が入らない | docker buildx の cache 判定 | `docker compose ... -p board-system-<color> build --no-cache backend` |
| 旧 v2.x.x が auto-update に反応しない | 旧 `update_check_url` が `.co.jp` を見ており、cert 期限切れ + DNS 撤去後は到達不能 | v3.0.0 を手動配布で新 URL へ橋渡し (済) |
| ショートカット連打でミニポート/トレイが増殖 | 単一インスタンス制御の欠落 | v3.0.1 で修正済み |
| 「更新あり」トーストは出るがダウンロードが走らない | サーバの msi ファイル名と `latest.json` の `url` が不一致 (404) | サーバ上のファイル名と `latest.json` の `url` を揃える (バージョン付き名で統一) |
| 新規依存 (例: python-socketio) が msi にバンドルされない | ビルド時に `pip install -r requirements.txt` が走っていない / setup.py の includes に未追加 | (1) build_msi.ps1 が requirements.txt を install しているか (2) setup.py の `includes` / `packages` に新規パッケージ追加。build_msi.ps1 末尾の検証で socketio/engineio ディレクトリ存在チェック済 |
| auto-update 後にユーザ設定 (features 等) が初期値に戻る | msi に `config.json` をバンドルしていて、上書きインストールで既存設定が消える | **v3.1.4 で修正済**: setup.py から config.json バンドルを除外し、config_loader の defaults を本番 URL に。既存ユーザの config.json は msi で触られない |

## ロールバック

- 旧 msi (v2.2.2) は msi のキャッシュにあるはずだが、念のため Git の `git show HEAD~:wl_desktop_app/version.py` を確認しながら旧 commit に checkout して旧 msi をビルドする手順を用意しておく
- 旧版を再配布する場合は `latest.json` を旧 version に戻すだけで全端末がダウングレード自動更新する (`is_newer` は新→旧でも `True` を返さないので注意)
  - 強制ダウングレードしたい場合は、ユーザー側で msi を手動再インストール
