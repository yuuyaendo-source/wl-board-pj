# デプロイとマイグレーション手順

修正済みマイグレーション（`g7b8c9d0e1f2` の IF NOT EXISTS 対応）を本番に反映し、`alembic upgrade head` で同じ事象を防ぐ手順です。

---

## 前提

- 本番サーバー: `wlboardsys-app-01`
- プロジェクト配置: `/var/www/wlinko-pj`（または `wlinko-pj` を clone したディレクトリ）
- バックエンドコンテナ: `linko-backend-blue`（`COLOR=blue` の場合）
- バックエンドのコード: `board-system/backend` をビルドした Docker イメージ

---

## Step 1: ローカルで修正をコミット・プッシュ

開発マシン（linko-system / wl-board-pj を編集している環境）で実施します。

```bash
cd /home/hisashi/dev/wl-board-pj

# 変更確認
git status
git diff board-system/backend/alembic/versions/g7b8c9d0e1f2_add_oauth_pkce_state.py

# コミット
git add board-system/backend/alembic/versions/g7b8c9d0e1f2_add_oauth_pkce_state.py
git commit -m "fix(alembic): oauth_pkce_state を CREATE TABLE IF NOT EXISTS に変更"

# リモートへプッシュ（main またはデプロイ用ブランチ）
git push origin main
```

※ リポジトリが GitHub / GitLab 等にある場合、プッシュ先は利用しているブランチに合わせてください。

---

## Step 2: 本番サーバーにログインし、リポジトリを更新

本番サーバーで、デプロイ元のディレクトリに移動して pull します。

```bash
ssh devuser01@wlboardsys-app-01

cd /var/www/wlinko-pj
# または: cd /var/www/wl-board-pj  など、実際のプロジェクトパスに合わせる

git pull origin main
```

※ デプロイ用ブランチが `main` でない場合は、そのブランチを pull してください。

---

## Step 3: バックエンドの Docker イメージを再ビルド

Compose でバックエンドだけビルドし直します。本番用の compose ファイル名は環境に合わせて読み替えてください。

```bash
# board-system ディレクトリに移動
cd /var/www/wlinko-pj/board-system
# もしくは: cd board-system  など

# 本番用 compose でバックエンドのみビルド（キャッシュを使わず最新コードで）
docker compose -f docker-compose.prod.yml build --no-cache backend
```

- `COLOR` 等の環境変数が必要な場合は、`.env` を読み込むか、実行前に export してください。  
  例: `export COLOR=blue` のうえで上記を実行。

---

## Step 4: バックエンドコンテナを新しいイメージで起動

既存のバックエンドコンテナを止め、同じ compose で起動し直すと新しいイメージでコンテナが作られます。

```bash
# 同じ board-system ディレクトリで
docker compose -f docker-compose.prod.yml up -d backend
```

- コンテナ名が `linko-backend-blue` のままになるよう、`COLOR=blue` 等の設定を合わせておいてください。
- blue/green やロードバランサの切り替え手順がある場合は、その手順に従って「新しい backend」がトラフィックを受けるようにしてください。

---

## Step 5: コンテナ内でマイグレーションを実行

新しいコンテナには修正済みの `g7b8c9d0e1f2_add_oauth_pkce_state.py` が含まれているので、`upgrade head` でエラーにならずに `placement_source` まで適用されます。

```bash
docker exec -it linko-backend-blue alembic -c /app/alembic.ini upgrade head
```

- 成功時は次のようなログが出ます:
  - `Running upgrade f6a7b8c9d0e1 -> g7b8c9d0e1f2, add oauth_pkce_state ...`
  - `Running upgrade g7b8c9d0e1f2 -> h8c9d0e1f2a3, add placement_source ...`
- `oauth_pkce_state` が既に存在する場合は g7b8c9d0e1f2 でテーブル作成はスキップされ、続けて h8c9d0e1f2a3 で `board_placements.placement_source` が追加されます。

---

## 動作確認

1. **API の応答確認**
   - パーソナルボード: `GET /boards/personal?owner_id=5` が 500 ではなく 200 で返ること。
   - 必要に応じてフロントからパーソナルボードを開いて表示を確認。

2. **DB の確認（任意）**
   - PostgreSQL に接続し、`board_placements` に `placement_source` カラムがあることを確認:

   ```bash
   docker exec -it linko-db psql -U linko_user -d linko_board_system -c '\d board_placements'
   ```

   - 一覧に `placement_source | character varying(32) | nullable` が出ていれば OK です。

## よくあるパターン（環境に応じて読み替え）

| 項目 | 例 |
| ------ | ----- |
| Compose ファイル | `docker-compose.prod.yml` / `docker-compose.staging.yml` など |
| 環境変数 | `COLOR=blue` を `.env` に書くか、`export` してから compose 実行 |
| デプロイ用ブランチ | `main` / `master` / `release` など |
| ビルドコマンド | `docker compose build backend` や CI で `docker build -f backend/Dockerfile .` など |

---

## トラブル時

- **「relation oauth_pkce_state already exists」がまだ出る**  
  → コンテナが古いイメージのままの可能性があります。  
  `docker images` でイメージの作成日を確認し、Step 3 のビルド後に Step 4 で確実にそのイメージで起動しているか確認してください。

- **「column board_placements.placement_source does not exist」がまだ出る**  
  → Step 5 の `alembic upgrade head` がまだ実行されていないか、別の DB を見ている可能性があります。  
  コンテナ内の `DATABASE_URL` と、実際にアプリが接続している DB が同じか確認し、再度 Step 5 を実行してください。

- **stamp で合わせたあと、再度 upgrade head したい**  
  → 既に `stamp g7b8c9d0e1f2` で合わせてある場合は、修正済みイメージをデプロイしたうえで、そのまま `alembic upgrade head` を実行すれば `h8c9d0e1f2a3` だけが適用されます。

## 付箋ボード（wl-sticky-note）のデータ永続化とバックアップ

デプロイのたびに付箋が消えないよう、**blue/green で共有する外部ボリューム**を使い、**デプロイ前に自動バックアップ**するようにしています。

### 初回のみ: 共有ボリュームの作成

`docker-compose.prod.yml` で付箋データは `sticky_note_data` という**外部ボリューム**を参照します。**初回デプロイ前**にサーバーで 1 回だけ実行してください。

```bash
docker volume create sticky_note_data
```

既に blue または green で付箋データがある場合、`deploy.sh` が現在の色のボリュームから `sticky_note_data` へコピーするため、初回実行後も付箋は維持されます。

### 自動バックアップ

- **タイミング**: `deploy.sh` 実行時、新コンテナ起動前に「現在の付箋コンテナ」から `boards.json` をコピーします。
- **保存先**: `board-system/backups/sticky-note/boards_YYYYMMDD_HHMMSS.json`
- **保管数**: 直近 30 件を残し、それより古いファイルは自動削除されます。

### 手動バックアップ

```bash
# 現在の付箋コンテナからコピー（blue の場合）
docker cp linko-sticky-note-blue:/app/data/boards.json ./backups/sticky-note/boards_$(date +%Y%m%d_%H%M%S).json
```

### リストア（付箋データを戻す）

1. 復元したいバックアップファイルを選ぶ（例: `board-system/backups/sticky-note/boards_20260306_120000.json`）。
2. 共有ボリュームに書き込むため、一時コンテナでコピーします。

```bash
cd /var/www/wlinko-pj/board-system

# 例: boards_20260306_120000.json を復元する場合
docker run --rm \
  -v "$(pwd)/backups/sticky-note/boards_20260306_120000.json:/src/boards.json:ro" \
  -v sticky_note_data:/data \
  alpine cp /src/boards.json /data/boards.json
```

1. 付箋コンテナを再起動すると、復元した内容が反映されます。

```bash
# 現在トラフィックを受けている方のコンテナを再起動（例: blue）
docker restart linko-sticky-note-blue
```
